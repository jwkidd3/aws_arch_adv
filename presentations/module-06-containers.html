📍 ECS, EKS, Fargate — how they relate

Two orchestrators, two launch types

ECS and EKS are the orchestrators. EC2 and Fargate are the launch types. You pick one orchestrator and one launch type. Fargate runs tasks/pods without you owning the host.

ECSEKS
Control planeAWS-native, freeManaged Kubernetes, hourly cost
Learning curveLow if you know AWSHigher — full Kubernetes API

📦 Amazon ECR — where images live

Capabilities

  • Private and public registries
  • IAM-controlled push and pull
  • Image scanning (basic + enhanced via Inspector)
  • Lifecycle policies to age out tags

Push flow

  • aws ecr get-login-password
  • docker build -t app:tag .
  • docker tag app:tag <repo-uri>
  • docker push <repo-uri>
Habit to teach: immutable tags + a lifecycle policy that keeps the last 30 images. "latest" is for laptops, not registries.
Lab 6 walks through this exact push flow. Pre-flight: confirm Docker is available in Cloud9 / CloudShell and the learner has ECR push permissions on their prefix.

⚡ AWS Fargate — serverless containers

You declare CPU and memory. AWS finds the host.

No EC2 instances to patch, no ASG to size, no Container Instances tab to babysit. Per-second billing for CPU + memory + storage. Works with both ECS and EKS.

Reach for it when

  • Variable workload, no steady-state floor
  • Small platform team
  • You don't need DaemonSets / GPUs / specialized AMIs

Stay on EC2 launch type when

  • Steady, predictable load (RIs/Savings Plans win)
  • GPU, Inferentia, or instance-store needed
  • You need to run privileged containers
Fargate Spot exists for ECS — up to 70% off, but tasks can be interrupted. Mention it; it returns in Module 12 (cost optimization).

🌐 Container networking with awsvpc mode

One ENI per task, real VPC IPs, real security groups

In awsvpc network mode (the default and only option for Fargate), each task gets its own ENI in your VPC. Tasks are first-class VPC citizens — they have security groups, flow logs, and can hit gateway endpoints directly.

Plan IPs accordingly: /24 subnets fill up fast at 100 tasks. Use larger subnets (/22 or /20) for production task fleets.
ENI-per-task limit: EC2 launch type has a per-instance ENI cap. Fargate doesn't — another reason it's the default for sprawling task counts.
Pre-Fargate ECS used bridge mode and shared the host ENI — tasks couldn't have their own SG. awsvpc mode is what made ECS production-grade.

🔑 IAM for tasks — two roles, two purposes

Task execution role

Used by the agent — pulls the image from ECR, writes container logs to CloudWatch, fetches Secrets Manager values referenced in the task definition.

Task role

Used by your application code — the AWS SDK in the container picks up these credentials. Scope it to the resources the app actually needs.

Anti-pattern: baking AWS access keys into the image or task definition. Use the task role — it gives you rotating, per-task credentials with CloudTrail attribution.
Get this distinction right and learners will stop putting access keys in environment variables. Repeat it: execution role = agent, task role = your code.

🚀 Deployment strategies

StrategyHow it worksRisk profile
RollingReplace tasks N at a time within one serviceDefault. Mixed versions live together briefly.
Blue/greenStand up the new version alongside; flip the ALB target group atomicallyCleanest rollback. Doubles cost during cutover.
CanarySend 5–10% of traffic to new version, observe, then promoteBest for high-risk releases. Needs metrics + alarms.
On AWS: ECS supports rolling natively; CodeDeploy drives blue/green and canary for ECS. We'll wire that up in Module 7.
Don't let rolling become "we just push and pray." Pair every rolling deploy with health checks and a circuit-breaker rollback — the ECS deployment circuit breaker does this for free.

🔌 Service mesh with App Mesh

What it gives you

  • Consistent traffic routing across services
  • Observability without changing app code
  • mTLS between services
  • Retries, timeouts, circuit breakers as config

Cost / complexity

  • Envoy sidecar per task (CPU + memory)
  • Another control plane to learn
  • Worth it past ~10 services with cross-traffic
Reality check: AWS announced App Mesh end-of-life. New designs lean to ALB-based routing or Kubernetes-native meshes (Istio, Linkerd) on EKS. Use the concept; check the current service map.
App Mesh is still in the AWS Advanced Architecting curriculum, hence its inclusion. Be honest about the deprecation — learners will look it up.

✅ Module recap

Pick the orchestrator first, the launch type second: ECS for AWS-native, EKS for Kubernetes-native; Fargate to skip host management.
Network and identity: awsvpc mode + task role — every task gets a real VPC ENI and its own IAM credentials.
Ship safely: rolling for routine, blue/green or canary for risky changes — CodeDeploy drives the latter (Module 7).
Hand off into Lab 6. Learners build, push, deploy — the whole loop in 45 minutes. Front-load the Docker build so the ALB is the climax.

🔧 Lab 6: Build & deploy a container

Image → ECR → ECS Fargate → ALB

  • Build the provided Docker image locally; tag it for your ECR repo
  • Authenticate to ECR (aws ecr get-login-password) and push the image
  • Run terraform apply to create the ECS cluster, Fargate service, task role, and ALB target group
  • Hit the ALB DNS name; verify the container responds; check CloudWatch Logs for the task output
Duration: ~50 minutes · Tag: Owner=<name> Course=archadv · Cleanup: terraform destroy + delete ECR images
Common stalls: Docker not running in Cloud9 (start it), ECR auth token expired (re-run get-login-password), task fails to pull image (wrong execution role). Have a cheat-sheet ready.
