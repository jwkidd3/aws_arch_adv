📚 The Well-Architected Framework

What it is

A set of questions AWS uses to evaluate workloads — structured around six pillars. The framework is a review lens, not an architecture pattern.

Use it as: a periodic workload review (every 6–12 months), a launch-readiness checklist, and a vocabulary your team shares when arguing trade-offs.
Most teams have heard of the framework but haven't actually used the tool. Free to use in the AWS console: Well-Architected Tool → define a workload → answer questions → get a heat-map of risks.

🏛️ The six pillars

Operational Excellence

Run and monitor systems to deliver business value; continuously improve.

Security

Protect information, systems, and assets while delivering value.

Reliability

Recover from failures, scale to demand, and avoid resource saturation.

Performance Efficiency

Use compute resources efficiently as demand and technology evolve.

Cost Optimization

Avoid unneeded costs; understand spend and where to allocate it.

Sustainability

Minimize environmental impact of running cloud workloads.

Sustainability was added in 2021 (the sixth pillar). Don't dwell on it — mention it exists, but the original five carry the bulk of audit weight.

⚙️ Operational Excellence

Design principles

  • Perform operations as code
  • Make frequent, small, reversible changes
  • Refine procedures frequently
  • Anticipate failure
  • Learn from operational events

AWS services that move the needle

  • CloudFormation / CDK / Terraform
  • Systems Manager (patching, automation)
  • CloudWatch + EventBridge
  • X-Ray for distributed tracing
"Operations as code" is the durable principle — it's what makes the other four achievable. Systems Manager is under-used; teams rebuild what it offers in custom scripts.

🔒 Security

Design principles

  • Implement strong identity foundation
  • Apply security at all layers
  • Automate security best practices
  • Protect data in transit and at rest
  • Prepare for security events

AWS services that move the needle

  • IAM Identity Center, IAM, SCPs
  • KMS, Secrets Manager, ACM
  • GuardDuty, Security Hub, Macie
  • VPC, WAF, Shield, Network Firewall
Coming up: Module 2 (Organizations & SCPs), Module 8 (WAF/Shield), Module 9 (KMS & Secrets Manager).
"Strong identity foundation" is the load-bearing principle — everything else fails open without it. Tease the multi-account discussion in Module 2.

🔥 Reliability

Design principles

  • Automatically recover from failure
  • Test recovery procedures
  • Scale horizontally to increase availability
  • Stop guessing capacity
  • Manage change in automation

AWS services that move the needle

  • Multi-AZ everything (RDS, ElastiCache, EFS)
  • Auto Scaling Groups, ELB, Route 53 health checks
  • S3 cross-region replication
  • AWS Backup, Resilience Hub
"Test recovery procedures" is what most teams skip — they have backups but don't restore from them. Resilience Hub is newer and worth a mention.

⚡ Performance Efficiency

Design principles

  • Democratize advanced technologies (managed services)
  • Go global in minutes
  • Use serverless architectures
  • Experiment more often
  • Mechanical sympathy — pick the right tool

AWS services that move the needle

  • Lambda, Fargate (covered in Module 6 & 11)
  • CloudFront, Global Accelerator
  • Aurora, DynamoDB, ElastiCache
  • Compute Optimizer for right-sizing
"Mechanical sympathy" — don't put OLTP traffic on Redshift; don't put analytics on DynamoDB. Module 10 is the expanded version of this.

💰 Cost Optimization

Design principles

  • Adopt a consumption model
  • Measure overall efficiency
  • Stop spending on undifferentiated heavy lifting
  • Analyze and attribute expenditure
  • Use managed services to reduce TCO

AWS services that move the needle

  • Cost Explorer, Budgets, Cost Anomaly Detection
  • Savings Plans, Reserved Instances, Spot
  • S3 Intelligent-Tiering, EBS gp3
  • Compute Optimizer
Coming up: Module 12 walks the cost tools end-to-end with a hands-on Cost Explorer report.
"Analyze and attribute" is the durable principle. Without tagging, every other cost lever is conjecture.

⚖️ The pillars conflict — that's the point

Pull APull BDecision lens
Reliability (multi-region)Cost (single region)RPO/RTO requirement vs. revenue at risk
Performance (provisioned)Cost (on-demand)Steady vs. spiky load shape
Security (private subnets only)Operational ease (public access)Threat model + bastion / SSM Session Manager
Performance (caching)Reliability (cache stampede)Cache stampede mitigation, TTL strategy
The framework's value: it makes the trade-offs explicit. The right answer is "we picked A because of B" — not "we have all six pillars covered."
This is the slide that distinguishes architects from builders. Discussion-worthy: ask the room which pull they live with most often.

📋 The Well-Architected Review process

  1. Define a workload — not the whole company; one workload
  2. Answer the questions per pillar (the WA Tool walks you)
  3. Generate the heat-map — high / medium / low risks per pillar
  4. Prioritize and address high risks; defer mediums with intent
  5. Re-review after major changes or every 6–12 months
A clean review surfaces 5–15 issues per workload — even on workloads the team thought were tight.
The Well-Architected Tool in the AWS console makes the review tractable — otherwise the framework feels like 200 pages of text.

🔧 Lab 1: Well-Architected VPC

Build the same VPC two ways — console and Terraform

  • Part A (console): VPC, public + private subnets, IGW, route table, EC2 in the public subnet
  • Part B (Terraform): review the provided HCL, terraform init & apply, verify the same topology in the console
  • Validation: SSH (or SSM) to the EC2; confirm reachability; terraform destroy when done
  • Discuss: which workflow do you reach for in production, and why?
Duration: ~50 minutes · Pair: Optional · Both Part A (console) and Part B (Terraform) — compare them
