📚 Core CI/CD concepts

Two ideas, one workflow

Continuous Integration — every commit triggers automated build + test. Continuous Delivery / Deployment — every passing build is releasable; deployment to production is one button (delivery) or zero buttons (deployment).

Why architects care: deploy frequency is the single best leading indicator of operational health. Teams that deploy daily recover from incidents faster — the DORA finding.
Through-line: Operational Excellence pillar (Module 1) "perform operations as code" lands here. The pipeline is the operations as code.
If the room hasn't read the Accelerate / DORA work, plant the seed — it reframes CI/CD as a business outcome, not a developer-tools concern.

🧰 The AWS code suite

CodeCommit

Managed Git. IAM-controlled. Replaces self-hosted Git for AWS-only shops.

CodeBuild

Managed build runners. buildspec.yml drives compile / test / package steps.

CodeDeploy

Pushes artifacts onto EC2, ECS, or Lambda. appspec.yml defines lifecycle hooks.

And the conductor: CodePipeline stitches a Source → Build → Test → Deploy graph and runs it on every source-stage change.
Service status note: AWS is sunsetting CodeCommit for new customers. The patterns still apply — substitute GitHub or GitLab as the source stage.
Learners may already use GitHub. Show CodePipeline can take GitHub via CodeStar Connections — the rest of the pipeline (Build/Deploy) doesn't change.

📝 buildspec.yml and appspec.yml

buildspec.yml (CodeBuild)

version: 0.2
phases:
  install:
    runtime-versions:
      nodejs: 20
  pre_build:
    commands:
      - npm ci
  build:
    commands:
      - npm test
      - npm run build
artifacts:
  files:
    - 'dist/**/*'
    - 'appspec.yml'

appspec.yml (CodeDeploy, ECS)

version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: <TASK_DEF_ARN>
        LoadBalancerInfo:
          ContainerName: web
          ContainerPort: 8080
These two files are the contract between humans and the pipeline. Pipeline JSON is the plumbing — these files are what developers actually edit.

☁️ CloudFormation as a pipeline action

Infrastructure changes are deployments too

CodePipeline has a first-class CloudFormation deploy action. Source repo holds the template; pipeline creates a change-set, optionally requires manual approval, then executes the change-set. Failures roll back automatically.

Why use it

  • Drift-free infrastructure
  • Change-set preview = peer review
  • Same auditability as application deploys

Lab note

  • CodeBuild stage runs cfn-lint or your linter of choice
  • Manual approval action
  • Second CodeBuild runs build in the console
Most rooms split — some teams CFN, some Terraform. The pipeline shape is identical; only the tool changes. Lean to whichever tool the learners use day-to-day.

🔒 Cross-account pipelines and OIDC

Cross-account deploys

  • Pipeline lives in a tooling account
  • Artifact bucket has a bucket policy granting target accounts read
  • Deploy actions assume a role in the target account (dev / stage / prod)
  • KMS key on the artifact bucket must be shared too

OIDC for GitHub Actions

  • GitHub issues a short-lived JWT per workflow run
  • Configure GitHub as an IAM identity provider
  • An IAM role trusts that JWT (scoped by repo / branch)
  • No long-lived access keys in GitHub secrets
Default to OIDC for any third-party CI hitting AWS. Static keys are an audit finding waiting to happen.
The OIDC pattern took years to standardize and is now the AWS-recommended way to integrate any third-party CI. Pin this slide for any learner currently using long-lived GitHub keys.

🪓 Secrets in pipelines

Where secrets belong

  • Secrets Manager — rotating creds, DB passwords
  • Parameter Store SecureString — cheap config + secrets
  • Both are referenced from buildspec.yml; values never hit logs

Where they don't belong

  • Plain CodeBuild environment variables (visible in logs)
  • Hardcoded in the source repo
  • Hardcoded in CloudFormation templates or pipeline variables
Pipeline IAM hygiene: the build role only needs secretsmanager:GetSecretValue on specific secrets — not *.
Module 9 goes deep on KMS / Secrets Manager. Today, the takeaway is "buildspec.yml can reference Secrets Manager directly — use that, not env vars."

✅ Module recap

The four services map to lifecycle stages: CodeCommit (source) → CodeBuild (compile/test) → CodeDeploy (release) → CodePipeline (the orchestrator across them).
Pick the deployment strategy by risk: rolling for routine, blue/green for atomic rollback, canary when alarms can vote on health.
Identity hygiene: OIDC for any third-party CI; cross-account pipelines via assumed roles; Secrets Manager for everything secret.
Hand off into Lab 7. Remind learners they're wiring four services live — the win is seeing the pipeline turn green end-to-end on a git push.
