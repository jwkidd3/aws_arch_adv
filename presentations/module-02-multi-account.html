🏢 Single to Multiple Accounts

Organizations, OUs, SCPs, and IAM Identity Center at scale

🧩 Why multiple accounts?

The account is the strongest isolation boundary in AWS

Stronger than VPCs, stronger than IAM roles. Use it on purpose — for blast-radius, billing, compliance, and team autonomy.

Security isolation

Prod cannot reach into dev. A compromised role in one account can't pivot to another.

Billing & chargeback

Per-account cost is the cleanest attribution unit. Tags help, accounts are definitive.

Service limits

Quotas are per-account-per-region. Splitting workloads side-steps the noisy-neighbor quota fight.

Push back on "one account per environment". Most mature orgs end up at 1 per workload-per-stage — dozens to hundreds of accounts. Account creation is free; it's IAM and SCPs that need design.

🏢 AWS Organizations

Core building blocks

  • Management account — payer, root of the org
  • Organizational Units (OUs) — hierarchical grouping
  • Member accounts — the workload accounts
  • Consolidated billing — one invoice, shared discounts

Common OU shapes

  • Security OU (log archive, audit)
  • Infrastructure OU (network, shared services)
  • Workloads OU — Prod / Non-Prod sub-OUs
  • Sandbox OU (this lab lives here)
  • Suspended OU (deprovision-on-the-way-out)
Rule of thumb: design OUs around policy needs, not around teams. Teams change; policy boundaries are durable.
The management account should run nothing — it's purely the org root. Resist the temptation to "just put one ALB in there." Once compromised, the management account compromises every member.

🔒 Service Control Policies

What SCPs are

  • Guardrails attached to OUs or accounts
  • Define the maximum permissions in an account
  • Deny-by-default: an SCP grants nothing — IAM still does the granting
  • Inherited down the OU tree (intersection)

Common patterns

  • Deny outside approved regions
  • Deny disabling CloudTrail / Config / GuardDuty
  • Deny root-user actions in member accounts
  • Restrict S3 buckets to encryption-required
Watch out: SCPs do not apply to the management account. Test with full ARN paths; never block AWS Support.
SCPs are an admission test, not an authorization. They restrict what IAM can authorize. If a developer says "IAM allows it but I get denied," 9 times out of 10 it's an SCP. Demonstrate the policy simulator if time permits.

👤 IAM Identity Center

One sign-in, every account

The successor to AWS SSO. A workforce identity store that federates into every account in the organization, with permission sets mapped to OU/account assignments.

Identity sources

  • Built-in directory
  • Active Directory (AD Connector or Managed AD)
  • External IdP via SAML 2.0 (Azure AD / Entra ID, Okta)

Permission sets

  • Reusable IAM policy bundles
  • Assigned per (group, account)
  • Provision IAM roles into target accounts on-demand
If learners still issue long-lived IAM users with access keys, this is the slide where you confront that. Identity Center plus short-lived role chaining is the right answer for human access. CLI v2 supports it natively (aws sso login).

🎪 AWS Control Tower

What it gives you

  • Opinionated landing zone (Security + Log Archive accounts)
  • Account Factory for vended accounts
  • Mandatory + optional guardrails (preventive SCPs and detective Config rules)
  • Drift detection

Trade-offs

  • Faster zero-to-multi-account than DIY
  • Less flexible — expects its own OU layout
  • Harder to retrofit onto an existing complex org
  • Customizations via CfCT or Account Factory for Terraform (AFT)
Greenfield? Start with Control Tower. Mature org? Layer Identity Center + SCPs onto your existing Organizations and skip the lift.

🧰 IaC across accounts

Provider aliasing

  • One aws provider per target account, distinguished by alias =
  • Each provider uses assume_role { role_arn = ... }
  • Resources select a provider with provider = aws.prod

Account vending in code

  • aws_organizations_account resource creates members
  • Bootstrap role (OrganizationAccountAccessRole) runs from the management account
  • Wire SCP attachments via aws_organizations_policy_attachment
Blast-radius warning: a single console cleanup with the wrong provider alias can wipe the wrong account. Use separate state files per account.
Show a 10-line provider block with two aliases live, if possible. State separation is the durable habit; aliases alone aren't enough — use one workspace or one state file per account.

📋 Centralized logging & monitoring

Log Archive account

Receives org-wide CloudTrail, Config snapshots, S3 access logs. Read-mostly.

Audit / Security account

Runs GuardDuty delegated admin, Security Hub aggregator, IAM Access Analyzer.

Member accounts

Forward logs out, run workloads, can't disable trail or stream.

Pro tip: enable an org-level CloudTrail from the management account so members literally cannot turn it off — pair with an SCP that denies cloudtrail:StopLogging.
This is the shape Control Tower bakes in by default. Even DIY orgs should adopt it — centralized logging is the single highest-leverage governance control.

✅ Module recap

Account = blast radius. Use OUs to group by policy need, not by team org chart.
SCPs guard, IAM grants. An SCP is a ceiling, not a permission. Consolidated billing comes free with Organizations.
Identity Center + permission sets replace long-lived IAM users for humans. Control Tower automates account vending if you're starting fresh.
