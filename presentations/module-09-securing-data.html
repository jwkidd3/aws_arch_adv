🔑 AWS KMS — the key concepts

Key types

  • AWS-owned — transparent, free, no visibility
  • AWS-managed — aws/<service>, free, auto-rotated
  • Customer-managed — your CMK, your policy, $1/mo

Patterns

  • Envelope encryption — KMS encrypts a data key; data key encrypts the data
  • Automatic annual rotation (CMKs)
  • Aliases — alias/orders-prod — outlive key IDs
  • Multi-region keys — same key material across regions
Envelope encryption is the model that makes KMS scale — KMS never sees your bulk data. Mention it explicitly; learners who skip the concept get confused later.

📝 Key policies vs IAM policies

The key policy is the source of truth

Unlike S3 buckets or other resources, a KMS key's key policy is the primary access control. IAM policies do not grant access to a key unless the key policy permits IAM to do so.

Key policy

  • Attached to the key itself
  • Required — every CMK has one
  • Must explicitly delegate to IAM if you want IAM principals to use the key

IAM policy

  • Attached to a user / role
  • Only effective when key policy allows IAM
  • Useful for cross-team grants once the key policy opens the door
Failure mode: remove the root principal from a key policy and you can lock yourself out of the key permanently. AWS will not bail you out.
This is the single highest-value slide in the module. Repeat the rule out loud: "key policy is the source of truth." Most learners come in thinking IAM is enough.

🔒 Secrets Manager — rotation as a feature

What it stores

  • DB credentials (RDS, Aurora, Redshift, DocumentDB)
  • API keys, OAuth tokens
  • Arbitrary key/value JSON
  • Encrypted with KMS — bring your own CMK

Rotation model

  • Lambda function rotates the secret on a schedule
  • AWS-provided templates for RDS / Aurora
  • Custom Lambda for anything else
  • Versioning — AWSCURRENT / AWSPENDING / AWSPREVIOUS
Apps fetch the secret at runtime via the SDK — no secret in env vars, no secret in source code, rotation is invisible to the app.
The four-stage version model (current/pending/previous) is what makes rotation safe — old connections finish on the previous version while new connections use the current.

Rule of thumb: if it rotates, Secrets Manager. If it doesn't, Parameter Store SecureString. Don't pay $0.40/mo for static config.
Many orgs use both — Secrets Manager for credentials, Parameter Store for everything else. That's the right pattern.

🛡️ CloudHSM — when KMS isn't enough

Why CloudHSM exists

  • FIPS 140-2 Level 3 — tamper-evident hardware
  • Single-tenant HSM appliance in your VPC
  • You hold the master keys — AWS cannot
  • PKCS#11, JCE, OpenSSL engine support

When to reach for it

  • Regulated workloads requiring FIPS 140-2 L3
  • Custom key store — KMS keys backed by your HSM
  • SSL/TLS offload, code signing, document signing CAs
  • Cross-cloud / on-prem key custody
Cost reminder: CloudHSM bills per-hour per HSM, in cluster, ~$1,800/month for a redundant pair. Default to KMS unless a control says you can't.
Almost everyone defaults to KMS and that's the right answer. CloudHSM is for the small set of regulated cases — payments, healthcare crypto, gov workloads.

🔐 Encryption at rest & in transit

At rest — KMS-integrated

  • S3 — SSE-S3, SSE-KMS, dual-layer (DSSE-KMS)
  • RDS / Aurora — encrypted at create time
  • EBS — default-encrypt at the account level
  • DynamoDB, EFS, FSx, Redshift — all KMS-aware

In transit — TLS via ACM

  • ACM provisions and renews public certs free
  • Attach to ALB, NLB, CloudFront, API Gateway
  • Private CA (ACM PCA) for internal mTLS
  • RDS / Aurora support TLS to the engine
Turn on EBS default encryption per region as a one-line account policy. There is no good reason to leave it off.
EBS default encryption is the easy win that surprisingly many accounts miss. Mention it as a "fix this on Monday" item.

🔍 Audit and detection

CloudTrail

Every KMS API call is logged — Encrypt, Decrypt, GenerateDataKey. Required for forensic answers like "who decrypted that file?"

GuardDuty

ML-based detection of unusual API patterns — credential exfil, anomalous decrypt volume, port-scanning. Always-on, low-friction.

Macie

Discovers and classifies sensitive data in S3 — PII, credentials, financial. Use to validate the classification table is reality.

The triad: CloudTrail tells you what happened, GuardDuty tells you it was unusual, Macie tells you what was at stake.
All three are easy to enable and cheap relative to a single incident. The combination is the audit story you'll need when compliance asks.

🔧 Lab 9: KMS + Secrets Manager

Build a CMK, encrypt an object, rotate a secret

  • Build a customer-managed KMS key with a key policy that delegates to your IAM role
  • Upload an object to S3 with --sse aws:kms --sse-kms-key-id alias/<your-cmk>
  • Store a placeholder DB password in Secrets Manager, encrypted with the same CMK
  • Trigger the provided rotation Lambda manually; observe AWSCURRENT / AWSPREVIOUS labels swap
  • Open CloudTrail and find the kms:Decrypt events from the rotation
Duration: ~50 minutes · Pair: Optional · Cleanup: schedule key deletion (7-day window) before console cleanup
Schedule key deletion not immediate delete — learners should see the 7-day pending-deletion window. The rotation Lambda is provided in the terraform/ directory.
