📂 Access patterns drive store choice

OLTP

Many small, latency-sensitive reads/writes. Strong consistency. Joins, transactions. Aurora, RDS, DynamoDB.

OLAP

Few, very large analytical queries. Columnar storage. Scan-heavy, write-light. Redshift, Athena over S3.

Event-driven

Append-only streams, fan-out, replay. Kinesis, MSK, EventBridge, S3 + Athena for replay-from-archive.

The diagnostic question: what does a typical read look like? One row by primary key? A 200-row aggregation across a partition? A 50M-row scan? The answer picks the store.
If learners can't answer "what does a typical read look like?", they're not ready to pick a store. Send them back to the requirements doc.

🌡️ Amazon Aurora

What it is

  • MySQL- and PostgreSQL-compatible
  • Storage decoupled from compute — scales to 128 TiB
  • Six-way replicated across 3 AZs at the storage layer
  • Up to 15 read replicas with sub-10ms replication lag

Variants

  • Provisioned — pick instance class
  • Serverless v2 — auto-scales ACUs in seconds
  • Global Database — cross-region, <1s replication, secondary RPO ~1s
Aurora gives you "RDS shape" (SQL, joins, transactions) with "cloud-native shape" (decoupled storage, fast replicas, point-in-time restore).
Aurora is the right default when the team is comfortable with SQL and the workload is OLTP. Don't push them to DynamoDB unless the access pattern argues for it.

⚡ Amazon DynamoDB

The shape

  • Key-value & document, fully managed NoSQL
  • Single-digit-millisecond reads at any scale
  • Partition key (+ sort key) drives distribution
  • Eventually consistent by default; strongly consistent on request

Capacity & acceleration

  • On-demand — pay per request, spiky workloads
  • Provisioned — cheaper at steady scale
  • DAX — in-memory accelerator, microseconds
  • Global Tables — multi-region active-active
DynamoDB rewards access-pattern-first design. Model the queries before you model the data. SQL habits hurt here.
"Single-table design" deserves a mention if the room is curious. The crucial point: DynamoDB is fast and cheap if you use it right, slow and expensive if you treat it like a relational store.

🌐 Aurora Global Database vs DynamoDB Global Tables

DimensionAurora Global DatabaseDynamoDB Global Tables
Data modelRelational (MySQL / PostgreSQL)Key-value / document NoSQL
Write topologySingle primary region; secondaries are read-onlyMulti-region active-active — write anywhere
Replication lagTypically < 1 secondTypically < 1 second
Conflict resolutionN/A (single writer)Last-writer-wins by timestamp
FailoverManual or managed; promote a secondary, RTO ~minuteNo failover — every region is live
Best forOLTP that needs SQL + cross-region read scale + DRGlobally distributed apps tolerating LWW conflicts
The centerpiece question: can your app live with last-writer-wins? If yes — DynamoDB Global Tables. If no — Aurora Global Database with a single primary.
This is the slide the module is built around. Linger here. Have learners commit out loud to which side their workload belongs on.

🚀 ElastiCache — Redis vs Memcached

DimensionRedisMemcached
Data structuresStrings, hashes, lists, sets, sorted sets, streamsStrings only
PersistenceOptional snapshots, AOFNone
Replication / HAMulti-AZ with automatic failoverSharding, no replication
Pub/sub, geo, streamsYesNo
Best forSession store, leaderboards, queues, rate-limitingPure cache for ephemeral KV
Pick Redis in 90% of new projects. Memcached only when you genuinely need horizontal-shard pure caching with no replication.
ElastiCache for Redis has effectively replaced Memcached for new builds. Mention Valkey briefly if learners ask — AWS now offers ElastiCache for Valkey as a Redis-compatible alternative.

🏪 Redshift & S3 as a data lake

Amazon Redshift

  • Columnar, MPP data warehouse
  • RA3 nodes — managed storage, decoupled compute
  • Redshift Spectrum — query S3 directly
  • Concurrency scaling for unpredictable BI load

S3 as a data lake

  • S3 + Glue Catalog + Athena = serverless lakehouse
  • Parquet / ORC for columnar efficiency
  • Lake Formation for fine-grained access
  • Pay only for queries scanned
For analytics that's mostly ad-hoc and intermittent, S3 + Athena beats a provisioned Redshift cluster on cost. For sustained BI dashboards, Redshift wins on query latency and concurrency.
The frame: Athena for "I run this query twice a week"; Redshift for "200 analysts hit this dashboard at 9am every day".

🎯 Picking a store — the decision lens

  1. What's the access pattern? OLTP, OLAP, event, hybrid?
  2. What's the consistency requirement? Strong, eventual, last-writer-wins?
  3. What's the scale? Rows / sec, GB / day, peak rps?
  4. What's the geography? Single region OK, multi-region read-only, multi-region active-active?
  5. What's the team? SQL-comfortable, NoSQL-comfortable, ops capacity?
The architect's job is to make the trade-off explicit. "We picked DynamoDB because we accept LWW for the global write surface" is the right shape of answer.

🔧 Lab 10: Build a data lake

S3 + Glue Crawler + Athena — SQL on files, no database

  • terraform apply -var "learner=<name>" — provisions an S3 lake bucket with seed CSVs, a Glue catalog DB, a Glue Crawler, and an Athena workgroup
  • Run the crawler in the Glue console; confirm the sales table and partition year=2024 appear in the catalog
  • Query in Athena: SELECT region, SUM(revenue) FROM sales WHERE year='2024' GROUP BY region
  • Drop a new CSV under sales/year=2024/; re-run the crawler; re-run the query — new rows appear without schema changes
  • Note Data scanned per query — that is the bill
Duration: ~30 minutes · Tag: Owner=<name> Course=archadv · Cleanup: empty the bucket then terraform destroy
The big "aha": no database was provisioned. Files in S3, catalog in Glue, query with Athena. That separation is the data-lake pattern. If a learner asks "why not just RDS" — the answer is the Data scanned metric and the schema-on-read flexibility.
