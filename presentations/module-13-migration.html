🚉 Migrating Workloads

The 7 Rs framework, MGN, DMS, DataSync — design choices first

Advanced Architecting on AWS — Module 13 of 14

🎯 Module objectives

  • Apply the 7 Rs framework — and tell the seven apart
  • Plan a discovery and assessment phase before any cutover
  • Pick the right tool: MGN for servers, DMS for databases, DataSync / Snow for bulk data

📍 The three phases

1. Assess

Inventory, dependencies, TCO. Output: a migration portfolio with per-workload R-strategy.

2. Mobilize

Landing zone, networking, security, pilot moves. Build the muscle on a low-risk workload first.

3. Migrate & Modernize

Wave-based execution. Each wave: cutover, validate, sunset on-prem. Modernize after stabilizing.

Discovery tools: AWS Application Discovery Service (agent-based or agentless), Migration Evaluator (free TCO modeling), AWS Migration Hub (single pane across waves).
Most failed migrations fail in Assess — teams jump to Mobilize without a real inventory and discover dependencies mid-cutover. Push the discipline of finishing Assess.

📋 The 7 Rs — one strategy per workload

StrategyWhat it meansWhen
RetireTurn it offNo one uses it; you just discovered that
RetainLeave on-prem (for now)Mainframe, regulatory hold, near end-of-life
RehostLift & shift — same OS, EC2Speed matters; modernization later
RelocateVMware-to-VMware on AWSVMware Cloud on AWS — preserve hypervisor
RepurchaseDrop and replace with SaaSEmail, CRM, HR — off-the-shelf wins
ReplatformLift & tinker — managed DB, etc.Move SQL Server → RDS without rewriting app
RefactorRe-architect for cloud-nativeStrategic apps that justify the spend
Drill the difference between Rehost / Relocate / Replatform / Refactor — that's where the room conflates. Repurchase is the cheapest "migration" of all and the room forgets it exists.

🔧 AWS migration tools

Servers & VMs

  • AWS MGN (Application Migration Service, formerly CloudEndure) — block-level replication, automated cutover, Rehost workhorse
  • VMware Cloud on AWS — Relocate strategy
  • Snowball Edge / Snow Family — offline transfer for slow links or air-gapped

Data & databases

  • DMS — continuous replication, homogeneous (Oracle → Oracle on RDS) and heterogeneous (Oracle → Aurora PostgreSQL)
  • Schema Conversion Tool (SCT) — pairs with DMS for engine changes
  • DataSync — NFS / SMB / S3 bulk transfer
MGN replaces what was CloudEndure — if learners are studying old material, the names confuse. DMS + SCT is the classic Oracle-to-Aurora-PostgreSQL story; that's the case the room asks about most.

💾 Oracle → Aurora PostgreSQL with DMS + SCT

The classic heterogeneous migration

SCT converts schema and PL/SQL to PostgreSQL syntax, flags non-convertible blocks, generates an assessment report. DMS streams data continuously while the source stays live — cutover is a small window when replication lag goes near zero.

Steps

  1. SCT assessment report
  2. Convert + manually fix flagged objects
  3. DMS full load + change capture
  4. Cut over when lag is acceptable

Watch out for

  • Stored procedures with Oracle-specific features
  • Sequences, triggers, sysdate semantics
  • Application driver (JDBC) changes
  • Replication slot bloat on the source
The interview question they'll get is "how do you migrate Oracle?" The answer is "DMS continuous replication + SCT for schema; cut over in a small window." Make them say it.

🔥 Migrate now, modernize later

Pattern: Rehost first to stop the on-prem clock, then modernize wave-by-wave. Modernization without migration drags the cutover by quarters; migration without modernization wastes the move.

Modernization opportunities

  • Stateless web tier → Lambda or Fargate
  • Self-managed DB → RDS / Aurora
  • Cron + scripts → Step Functions / EventBridge
  • NFS share → S3 + presigned URLs

Sequencing

  • Pilot light wave: 1 low-risk app
  • Wave N: 5–15 apps with shared dependencies
  • Each wave ends with a retro — tune the runbook
  • Sunset on-prem capacity as waves complete
"Migrate now, modernize later" is the durable principle — don't let perfect block good. Refactor is a long pole; only do it where it matters.

✅ Module recap

7 Rs: Retire, Retain, Rehost, Relocate, Repurchase, Replatform, Refactor — one strategy per workload, not one strategy per portfolio.
Tooling map: MGN for servers, DMS + SCT for databases, DataSync / Snow for bulk data, Migration Hub to track the wave.
Order of operations: Assess → Mobilize → Migrate (in waves) → Modernize. Skipping Assess is the most common failure mode.
Hand off into the design exercise. The exercise is what cements the 7 Rs — abstract definitions slide off, concrete decisions stick.

💡 Design exercise

Apply the 7 Rs to a real-ish workload mix

  • Scenario: a mid-size company has these workloads to move:
    • A 12-year-old Java monolith on Tomcat (still core to revenue)
    • An Oracle 11g database (license up for renewal)
    • An on-prem CRM (vendor is 5 years from EOL)
    • A nightly batch job written in Perl on an aging VM
    • A SharePoint server used by ~40 people
  • Pairs decide: which R per workload? Which AWS tool? What order?
  • Share-back: 2 minutes per pair, name and justify each strategy
Duration: ~20 min pair work + ~10 min share-back (~30 min activity) · No console · Whiteboard or shared doc
Push pairs to commit. The Perl batch job is a Retire candidate (or rewrite as a Lambda). SharePoint is Repurchase — M365. Oracle is the marquee Replatform / Refactor question. Java monolith is Rehost first, modernize later.
