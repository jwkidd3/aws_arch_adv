🔗 VPC peering — the simplest hop

One-to-one, no transitive routing

A peering connection is a private link between exactly two VPCs. If A peers with B and B peers with C, A still cannot reach C — you'd need a third peering A↔C.

Use it when

  • Small number of VPCs (<10)
  • Stable topology, infrequent changes
  • You want lowest cost per GB transferred

Avoid it when

  • You'll grow past ~15 VPCs (n² mesh)
  • You need shared inspection or central egress
  • Cross-account ownership shifts often
The "no transitive routing" rule is the single biggest tripwire. Make learners say it back to you before moving on.

🛒 Transit Gateway — the hub

One regional hub, thousands of attachments

TGW is a regional virtual router. VPCs, VPNs, Direct Connect gateways, and other TGWs (inter-region peering) attach to it. Routing is policy-driven via TGW route tables.

Two concepts to internalize: association (which route table an attachment uses for outbound lookups) and propagation (which attachments' routes get auto-installed in a route table).
Pricing reminder: attachment-hour + per-GB charges. Cheap is relative; mesh peering can be cheaper for tiny topologies, but TGW wins past ~10 VPCs operationally.
Draw association vs propagation on the whiteboard. This single distinction is what learners get wrong on Lab 5.

The pattern: separate route tables per environment, propagate shared services into both, do not propagate prod into nonprod or vice versa. Result: dev cannot reach prod, both can reach shared services.
This is exactly the topology learners will build in Lab 5. Tease that they'll prove the isolation by trying (and failing) to ping across environments.

🌐 Direct Connect Gateway

What it solves

  • One DX connection, many VPCs — even across regions
  • Pairs with TGW for hub-and-spoke at scale
  • Removes the per-VPC virtual-interface limit

Two attachment styles

  • Virtual Private Gateway — one VPC at a time (legacy)
  • Transit VIF + TGW — many VPCs via DXGW → TGW (current)
Hybrid recap (Module 3): S2S VPN over internet for low-cost / day-one; DX private fiber for predictable bandwidth and latency; combine with DXGW + TGW for fan-out.
DXGW is often confused with TGW — it's not a router, it's a gateway that lets a DX connection terminate against many VPCs. Pair the two for serious topologies.

🤝 VPC sharing via Resource Access Manager

One network team owns the VPC

RAM lets the network account share specific subnets with workload accounts. Workload accounts launch ENIs into those subnets but do not own the VPC, route tables, NAT, or peering.

Why it matters

  • Centralized CIDR plan, no overlap surprises
  • One NAT gateway shared across teams (cost)
  • Network controls live where they belong

What's still in the workload account

  • EC2, RDS, ECS tasks (ENI-bound resources)
  • Security groups created by the consumer
  • IAM & service-level config
Sharing requires AWS Organizations with all-features enabled. SCPs around RAM matter — share too much and you've effectively un-isolated accounts.

🔒 VPC endpoints — keep traffic off the internet

Gateway endpoints

Free. Route-table entries.

  • S3
  • DynamoDB

Interface endpoints

Hourly + per-GB. ENI in your subnet.

  • Most AWS services
  • Backed by PrivateLink

Endpoint services

Expose your NLB privately to other VPCs / accounts.

  • SaaS-style sharing
  • One-way connectivity
Default rule of thumb: use the gateway endpoint for S3/DynamoDB on every private VPC. It's free and removes a NAT hop.
PrivateLink is the load-bearing primitive — it's what makes interface endpoints and endpoint services work. Mention it as a name learners will see again.

🏠 Central egress and inspection patterns

One egress VPC, many spokes

Spoke VPCs have no IGW or NAT. They route 0.0.0.0/0 to the TGW; the TGW routes it to a centralized egress VPC that owns the NAT gateways and (optionally) AWS Network Firewall for east/west or north/south inspection.

Wins

  • One NAT bill instead of N
  • Central allow-list / inspection
  • Audit and DLP from one place

Costs

  • Extra TGW data-processing charge
  • One blast radius if egress VPC fails
  • Operational discipline required
Most organizations grow into central egress around 8–12 VPCs. Below that, per-VPC NAT is simpler and not meaningfully more expensive.

✅ Module recap

Decision lens: peering for tiny meshes; TGW once you cross ~10 VPCs or need cross-account at scale; DXGW + TGW when DX joins the picture.
Isolation lever: TGW route tables — associate one per environment, propagate shared-services into all, prod and nonprod stay apart.
Reduce blast and bill: gateway endpoints for S3/DynamoDB on every private VPC; central egress once the VPC count justifies it.

🔧 Lab 5: TGW isolation + S3 VPC endpoint

Two parts — isolation by design, then private S3 with a deny-by-default endpoint policy

  • Part A (~35 min) — TGW with prod-rt and nonprod-rt; shared-services reaches both, prod and nonprod cannot reach each other. Validate by ping.
  • Part B (~15 min) — Attach an S3 gateway VPC endpoint to the prod VPC with an endpoint policy allowing only the lab bucket. aws s3 ls on the lab bucket succeeds; on any other bucket returns AccessDenied.
  • Inspect the prefix-list route in the prod private subnet route table — that's the gateway endpoint at work.
  • Stretch: tighten the endpoint policy further with aws:PrincipalOrgID.
