🏢 HA fundamentals on AWS

Two axes of redundancy

HA on AWS is the product of multi-AZ (within a region) and multi-region (across regions). Most workloads need the first; a small set need both.

Multi-AZ — the floor

  • RDS Multi-AZ, ElastiCache, EFS
  • ASG across ≥ 2 AZs
  • ALB cross-zone load balancing

Multi-region — the ceiling

  • Route 53 latency or failover routing
  • S3 cross-region replication
  • Aurora Global Database, DynamoDB Global Tables
"Multi-AZ is free architecture; multi-region is paid architecture." Don't go multi-region without an RPO/RTO requirement and a budget owner.

Most learners reach for ALB by default and that's right. Mention Gateway Load Balancer briefly if asked — it's for inline appliance insertion, not application traffic.

📈 Auto Scaling Groups

Building blocks

  • Launch template — AMI, instance type, user data
  • Min / desired / max capacity
  • Subnets across ≥ 2 AZs
  • Target group attachment

Scaling policies

  • Target tracking — the default; pick a metric & target
  • Step scaling — for asymmetric scale-up vs scale-down
  • Scheduled — known traffic shape (business hours)
  • Predictive — ML-driven, forward-looking
Use warm pools when boot time is the bottleneck — pre-initialized instances, stopped, ready to start in seconds.
Target tracking on CPU at 50% is the right default for most apps. Step scaling matters when scale-up needs to be aggressive but scale-down should be slow.

🌐 Route 53 health checks & routing

Failover

Primary + secondary; secondary takes over when health check fails. RTO = TTL + detection time.

Latency-based

Send each user to the lowest-latency healthy region. Useful for global apps with regional stacks.

Weighted

Split traffic by percentage — canary deployments, gradual region cutover.

Health checks probe an endpoint (HTTP / HTTPS / TCP) every 10 or 30 seconds. Pair with CloudWatch alarms for paging.
Lower TTLs make failover faster but cost more in DNS queries. 60s is a reasonable production default.

Most workloads land at pilot light or warm standby. Active-active is appropriate for revenue-critical user-facing systems where every minute of outage is a board-level event.

💥 DDoS — the threat surface

Layer 3 / 4 attacks

  • SYN floods, UDP reflection, NTP / DNS amplification
  • Goal: saturate bandwidth or connection table
  • Defense: CloudFront / Global Accelerator + Shield

Layer 7 attacks

  • HTTP floods, slow-loris, application abuse
  • Goal: exhaust application or DB
  • Defense: WAF rate-based rules, bot control
The architecture rule: push the front door to the edge. CloudFront + Route 53 absorb floods that would otherwise hit your ALB and origin.
Most "DDoS" incidents teams see are L7 application abuse, not volumetric floods. WAF rate-based rules are usually the right first lever.

The price discussion: Advanced is real money. Justify with a revenue-impact threshold — above $X/hour of downtime cost, Advanced pays for itself on one event.
Have the price ready. Most learners assume Shield Advanced is the default; it isn't — it's a budget conversation with the business.

🔒 AWS WAF — managed rule groups

Where WAF attaches

  • CloudFront distributions (global)
  • Application Load Balancers (regional)
  • API Gateway, AppSync, Cognito User Pools

Rule sources

  • AWS-managed rule groups — Core, Known Bad Inputs, SQLi, XSS, Linux, IP reputation
  • AWS Marketplace rule groups (3rd-party)
  • Custom rules — rate-based, regex, geo-match
Start with managed: Core + Known Bad Inputs + SQLi. Run them in count mode first to see false positives before switching to block.
The "count first" discipline is what separates working WAF deployments from outage-causing WAF deployments. Always count, then block.

🛡️ Network Firewall, Firewall Manager, Lambda@Edge

AWS Network Firewall

VPC-level stateful firewall. Suricata-compatible rules, deep packet inspection, domain allow/block. Sits between subnets and the internet gateway.

AWS Firewall Manager

Cross-account, org-wide policy for WAF, Shield Advanced, Network Firewall, security groups. Auto-applies as new accounts onboard.

Lambda@Edge / CloudFront Functions

Run code at edge locations. Header rewrites, A/B routing, light auth checks. CloudFront Functions for ultra-cheap; Lambda@Edge for fuller runtime.

Multi-account orgs should run a Firewall Manager policy that pins a baseline WAF web ACL on every public ALB — new accounts inherit it automatically.
Firewall Manager is the under-used piece. Without it, security teams chase WAF compliance per account; with it, one policy enforces it.

✅ Module recap

HA shape: multi-AZ is the floor, multi-region is the ceiling. Pick a DR model that matches RPO/RTO — and test it.
DDoS shape: push the front door to the edge. CloudFront + WAF + Shield handle the bulk; Network Firewall covers east-west and egress.
Org shape: use Firewall Manager so new accounts inherit a baseline web ACL automatically — security at scale, not per-account whack-a-mole.

🔧 Lab 8: WAF + ALB + Auto Scaling Group

Build it, attack it, watch the block

  • Build a ALB + ASG (2 AZs, t3.micro web servers running a tiny Flask echo app)
  • Create a WAF web ACL with AWS-managed rule groups: Core, Known Bad Inputs, SQLi
  • Associate the web ACL to the ALB; enable WAF logging to CloudWatch Logs
  • Send a normal curl — observe a 200; send ?id=1' OR '1'='1 — observe a 403 from WAF
  • Open CloudWatch Logs Insights, filter for action = "BLOCK", identify which managed rule fired
Duration: ~50 minutes · Pair: Optional · Cleanup: console cleanup when the block is verified
Keep the ASG at min=desired=2 to avoid scaling churn during the lab. The "BLOCK" log entry is the moment of payoff — make sure every learner sees it before destroying.
