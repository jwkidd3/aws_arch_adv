⚡ Stateless compute is the foundation

Why stateless wins at scale

Any instance can serve any request. Failures are recoverable by replacement. Autoscaling is just a count change — no state migration, no warm-up choreography.

Where state goes

  • Sessions → ElastiCache (Redis) or DynamoDB
  • User uploads → S3 (presigned URLs)
  • Long-running work → SQS + Step Functions

Patterns to avoid

  • Sticky sessions on the load balancer
  • Local disk caches that diverge per node
  • Singletons that block horizontal scale
"Where state goes" is the slide that unlocks the rest. If a team can't answer this question, autoscaling triggers don't matter yet.

📊 Autoscaling triggers — pick the right signal

TriggerBest forWatch out
CPU utilizationCompute-bound workloadsMisleading on I/O-bound apps
Memory (CloudWatch agent)JVM, Node, Python appsNot a default metric — agent required
Custom CloudWatch metricQueue depth, business KPILag if metric publish is sparse
Requests-per-target (ALB)Web tiers behind ALBMost-used in practice — tracks user pain directly
Default to requests-per-target for web tiers. CPU and memory are secondary signals; they tell you why scaling fired, not whether it should.
This is the slide most teams need. CPU is the trigger people reach for because it's the default — and it's wrong for most web workloads. Make them say "requests-per-target" out loud.

🔄 Event-driven design

SNS

Pub/sub fan-out. One publisher, many subscribers. Use when downstreams are independent.

SQS

Durable queue. Producer-consumer decoupling, retries, DLQs. Use when downstream may lag.

EventBridge

Schema-aware event bus. Rule-based routing, SaaS integrations. Use for workflow orchestration.

Decoupling buys you: independent scaling per service, retries without caller awareness, easier blue/green per consumer, and a clean failure boundary.
Most teams over-pick SNS. EventBridge replaces a lot of glue code. SQS is the boring durable choice and usually correct.

🚀 Serverless & microservices

Serverless building blocks

  • Lambda — per-request compute, no server fleet
  • Step Functions — orchestrate multi-step async flows
  • API Gateway — front door + throttling + auth
  • Aurora Serverless v2 — pay for capacity used

Microservices on containers

  • ECS / EKS for long-running services
  • Service discovery via Cloud Map or service mesh
  • API Gateway or ALB as ingress
  • Per-service deploy pipeline (Module 7)
Don't religious-war serverless vs. containers. Real systems mix. Ask the room how their teams split — usually edge APIs are Lambda, core services are containers.

💾 Caching at every tier

LayerServiceWhat it caches
EdgeCloudFrontStatic assets, cacheable HTML, signed URLs
ApplicationElastiCache (Redis / Memcached)Session state, computed results, hot keys
DatabaseDAX (DynamoDB)In-memory acceleration for DDB reads
Cache stampede: when a popular key expires and 10,000 clients miss simultaneously. Mitigate with jittered TTLs, request coalescing, or pre-warming.
Caching is a reliability lever as much as a performance one — until it isn't. Stampedes can take a database down faster than the un-cached load did.

🌎 Route 53 — latency vs. geolocation

Latency-based routing

  • Routes to the lowest-latency Region for the resolver
  • Optimizes for user experience
  • Default for global web apps

Geolocation routing

  • Routes by the resolver's country / continent
  • Optimizes for data residency / compliance
  • Use when EU users must hit eu-* Regions
Pick latency unless you have a reason to pick geo. Geo wins when regulation or licensing forces hard borders — otherwise latency gives better UX.
The room conflates these constantly. Geolocation is a compliance tool; latency is a performance tool. Pair with health checks for failover either way.

🔎 Observability at scale

Metrics

CloudWatch — system + custom metrics, alarms, composite alarms.

Tracing

X-Ray + OpenTelemetry — request flow across services, latency hotspots.

Logs

CloudWatch Logs Insights, structured logging, log-to-metric filters.

Cost lever: Graviton2 across the fleet (~20% cheaper, comparable perf), Fargate Spot for batch and dev, S3 Intelligent-Tiering for asset stores.
Observability is the price of admission for microservices — if you can't trace a request, you can't debug it. OpenTelemetry is the durable bet across vendors.

✅ Module recap

Stateless first: push state to ElastiCache, DynamoDB, or S3 — then autoscaling becomes a count change.
Requests-per-target is the trigger most web tiers should reach for — CPU is a backup signal, not the primary.
Design for failure: queues between services, jittered cache TTLs, multi-AZ everywhere — assume every dependency will misbehave.
Hand off into the design exercise. Don't over-build the recap — the exercise is the assessment.

💡 Design exercise

Pair up — design a multi-tier autoscaling architecture

  • Scenario: a global e-commerce site, ~5M MAU, traffic spiky around launches, EU + US user base
  • Decide: autoscaling triggers per tier (CPU / memory / custom metric / requests-per-target)
  • Decide: Route 53 latency vs. geolocation — justify the choice
  • Sketch: web tier, app tier, data tier, caching layer, queues between async paths
  • Share-back: 90 seconds per pair, room asks one challenge question
Duration: ~12 min pair work + ~8 min share-back (~20 min activity) · No console · Whiteboard or shared doc
Push pairs to commit to one trigger per tier. No "it depends." If they pick CPU for the web tier, ask why — the answer is usually because it was the default. Pull them back to requests-per-target.
