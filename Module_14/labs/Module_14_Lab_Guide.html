Advanced Architecting on AWS

Module 14 — Capstone: design, then build one slice

Objective

Synthesize the course. Each pair sketches a 3-tier architecture for the scenario brief, then picks ONE of three build slices to console-build in their own Sandbox. End with a short walkthrough explaining design decisions.

The point is the design conversation + one quality build slice, not getting a full multi-tier app online in 75 minutes.

Time budget: 75 minutes total

  • 20 min — framing, course recap, scenario brief, Q&A
  • 15 min — paired diagram (sketch the full 3-tier design)
  • 25 min — paired console build of one slice (Slice A, B, or C below)
  • 15 min — pair walkthroughs (3 pairs × 5 min, picked by the instructor)

Pre-flight

  1. Sign in to Sandbox<N>. Confirm role badge top-right reads AWSAdministratorAccess @ Sandbox<N>.
  2. Region: US East (N. Virginia) us-east-1.
  3. Pair up with the person next to you (or solo if odd).
  4. Have a diagram tool ready: whiteboard, draw.io, Excalidraw, Lucidchart — anything that lets you sketch boxes and lines.
  5. Confirm the Lab 1 VPC is still up — you'll reuse it. VPC → Your VPCs, find Name tag archadv-<you>-vpc.

Scenario brief

WidgetCo sells configurable industrial widgets through a public web store and a private partner portal. Both are read-heavy with bursty write spikes around new product launches. Target: 99.95% availability. Data is partner-PII (contact info, contract terms — not financial or health).

Today they run two ASP.NET apps on a fleet of 12 EC2s, one shared MySQL on EC2, and an S3 bucket for product images. They're growing 30% YoY.

Diagram requirements (15 min)

The full 3-tier diagram for WidgetCo must include all of these boxes on paper:

  1. Network — VPC layout (public / private subnets, AZ count, routing)
  2. Edge — CloudFront in front of the public web store; WAF on the origin
  3. Web tier — ALB + ASG (or Fargate)
  4. App tier — separated from the web tier (private subnets, separate SG)
  5. Database tier — Aurora MySQL multi-AZ with reader endpoint
  6. Object storage — S3 for product images, with CloudFront origin access control
  7. Secrets — Secrets Manager backed by a customer- managed KMS CMK
  8. Observability — CloudWatch alarms + log groups
  9. CI/CD — CodePipeline (or equivalent) — sketched, not built
  10. Cost guardrails — the Budget from Lab 12 + tagging strategy

Build slices: pick exactly one (25 min)

Each slice is sized to fit in 25 min if the diagram work was focused. Pick the slice that locks in the part of the course you most want to revisit.

Slice A — Edge + web (CloudFront → S3 static origin)

Best for pairs who want to revisit CloudFront, S3, OAC, and WAF mental models.

  1. S3 → Create bucket: archadv-<you>-cap-web. Block all public access (default).
  2. Upload a one-file index.html (CloudShell): echo "<h1>WidgetCo</h1>" > /tmp/index.html ; aws s3 cp /tmp/index.html s3://archadv-<you>-cap-web/
  3. CloudFront → Create distribution:
    • Origin: Choose S3 bucket → archadv-<you>-cap-web.
    • Origin access: Origin access control settings (recommended) → Create new OAC, defaults, Create.
    • Viewer protocol policy: Redirect HTTP to HTTPS.
    • Web Application Firewall (WAF): Enable AWS WAF security protections with Use monitoring protections only (creates a default web ACL with managed rules in Count mode).
    • Default root object: index.html.
    • Create distribution.
  4. When prompted at the top of the distribution detail page, copy the recommended bucket policy and paste it into S3 → bucket → Permissions → Bucket policy → Edit. Save. This is what lets CloudFront read the otherwise-private bucket via OAC.
  5. Distribution propagation is asynchronous (5–15 min). You do not need it Deployed by the end of the slot — note its Distribution domain name for your walkthrough.

Slice B — Web (ALB + ASG, using the Lab 1 VPC)

Best for pairs who want to revisit launch templates, target groups, and scaling. This is essentially the Lab 11 setup with no scaling policy — drop the load-generation step.

  1. Launch template archadv-<you>-cap-lt, AMI Amazon Linux 2023, instance type t3.small, SG with no inbound (added in step 3), IAM profile with AmazonSSMManagedInstanceCore, user data:
#!/bin/bash
dnf install -y httpd
systemctl enable --now httpd
echo "<h1>WidgetCo capstone</h1>" > /var/www/html/index.html
  1. ALB archadv-<you>-cap-alb, internet-facing, in both Lab 1 public subnets, ALB SG with HTTP from 0.0.0.0/0. Target group archadv-<you>-cap-tg (instances, HTTP, port 80, health check /).
  2. ASG SG: HTTP from the ALB SG (not 0.0.0.0/0).
  3. ASG archadv-<you>-cap-asg, launch template above, the same two public subnets, attach to the target group, desired/min/max = 2/2/2. ELB health checks on.
  4. Wait until 2 instances are InService + Healthy. Hit the ALB DNS name from CloudShell: curl http://<alb-dns>/ → "WidgetCo capstone".

Slice C — Data protection (KMS + Secrets Manager + S3)

Best for pairs who want to revisit Lab 9 in capstone scope. This slice is essentially a fast replay of Lab 9 Part A + B, with the KMS key reused across both an encrypted S3 bucket and the secret.

  1. KMS CMK archadv-<you>-cap-key (Symmetric, Encrypt and decrypt; admin + user = your IdC SSO role).
  2. S3 bucket archadv-<you>-cap-data with default encryption SSE-KMS pointing to that CMK (Bucket Key enabled).
  3. Upload a sample file from CloudShell; confirm head-object shows SSE: aws:kms.
  4. Secrets Manager secret archadv-<you>-cap-db-pass encrypted with the same CMK; key/value {"username":"app","password":"INIT"}; rotation disabled.
  5. Manually edit the password to ROTATED; confirm aws secretsmanager get-secret-value shows the new value and the Versions tab shows AWSCURRENT + AWSPREVIOUS.

Do not pick Aurora as a slice. Aurora multi-AZ cluster create alone is ~15 min and routinely overruns. If your pair wants to "see" Aurora, the instructor will demo from the management account during the walkthrough block.

Decisions you must justify in your walkthrough

Regardless of which slice you built, your walkthrough must answer:

  1. Why AZ count = 2 vs 3? (cost vs availability trade-off)
  2. Why Aurora vs RDS MySQL? (read replicas, failover, cost)
  3. Why CloudFront in front of the ALB? (latency, DDoS absorption, edge caching)
  4. Where does Secrets Manager hold what?
  5. What would you cut first under cost pressure?

Walkthrough format (15 min)

Three pairs are picked at random. Each gets 5 min:

  • 1 min — scenario interpretation
  • 2 min — diagram tour
  • 1 min — which slice you built and what you saw working
  • 1 min — the decision you debated longest

The room offers one constructive question per walkthrough.

Cleanup — DO BEFORE LEAVING THE ROOM

Whichever slice you built:

Slice A (CloudFront + S3):

  1. CloudFront → distribution → Disable. (Disabling takes ~5 min; deletion takes another 5–15 min after that — that's normal. You don't need to wait; it'll continue in the background.)
  2. Once disabled, click Delete on the distribution.
  3. S3 → archadv-<you>-cap-web → Empty, then Delete.
  4. If a default WAF web ACL was created (WAF & Shield → Web ACLs, region Global (CloudFront)), delete the ACL after the distribution is gone.

Slice B (ALB + ASG):

  1. ASG → set desired/min/max all to 0 → Delete.
  2. ALB → Delete; Target group → Delete.
  3. Launch template → Delete.
  4. SGs: delete ASG SG first, then ALB SG.

Slice C (KMS + Secrets Manager):

  1. Secrets Manager → secret → Delete, waiting period 7 days (minimum).
  2. S3 → cap-data bucket → Empty, then Delete.
  3. KMS → CMK → Schedule key deletion, waiting period 7 days.

Do NOT delete the Lab 1 VPC. The instructor cleans up VPCs centrally after class.

Keep the Lab 12 Budget alarm.
