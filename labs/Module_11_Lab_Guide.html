Advanced Architecting on AWS

Lab 11 — ASG with target-tracking scaling on request count

Objective

Build an ALB + ASG that scales on request-count-per-target (not CPU). Generate load and watch the ASG add an instance. The durable lesson: scale on the metric that leads saturation, not the one that lags it.

Time budget: 25 minutes build + 5 min discussion

Throughout, replace <you> with your slug. Region: us-east-1. We will use the Lab 1 VPC (2 public + 2 private subnets, NAT in 1 public subnet, IGW attached) that's still up from Day 1.

Pre-flight

  1. Sign in to Sandbox<N>. Confirm role badge top-right reads AWSAdministratorAccess @ Sandbox<N>.
  2. Region: US East (N. Virginia) us-east-1.
  3. Open CloudShell.
  4. Locate your Lab 1 VPC. Navigate VPC → Your VPCs. Note the VPC ID with Name tag archadv-<you>-vpc (Lab 1's). Note the IDs of its two public subnets — these are where both the ALB and the ASG instances will live in this lab. (Public subnets sidestep the NAT egress path for SSM/yum, which keeps the lab focused on scaling, not networking.)

Steps

1. Launch template (3 min)

  • Navigate: EC2 → Launch Templates → Create launch template.
  • Launch template name: archadv-<you>-lab11-lt
  • Application and OS Images (AMI): click Quick Start → Amazon Linux, then in the AMI dropdown pick the entry labeled Amazon Linux 2023 AMI (HVM) — Kernel 6.1, SSD Volume Type (Free tier eligible).
  • Instance type: t3.small
  • Key pair (login): Don't include in launch template (SSM only — no SSH).
  • Network settings:
    • Subnet: Don't include in launch template (ASG chooses).
    • Firewall (security groups): Create security group
      • Name: archadv-<you>-lab11-asg-sg
      • Description: ASG SG for lab 11
      • VPC: the Lab 1 VPC you noted above
      • Inbound: leave empty for now (we'll add the ALB-SG rule in Step 2 after the ALB SG exists).
      • Outbound: leave the default (all traffic to 0.0.0.0/0).
  • Advanced details:
    • IAM instance profile: pick any role that has AmazonSSMManagedInstanceCore attached. If none, navigate IAM → Roles → Create role → AWS service → EC2, attach AmazonSSMManagedInstanceCore, name it archadv-<you>-ssm-role, return to this dropdown.
    • User data — paste exactly:
#!/bin/bash
dnf install -y httpd
systemctl enable --now httpd
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
ID=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id)
echo "<h1>archadv $ID</h1>" > /var/www/html/index.html
  • Click Create launch template.

2. ALB + target group (6 min)

  • Navigate: EC2 → Load Balancers → Create load balancer → Application Load Balancer → Create.
  • Load balancer name: archadv-<you>-lab11-alb
  • Scheme: Internet-facing (default).
  • IP address type: IPv4 (default).
  • Network mapping:
    • VPC: Lab 1 VPC
    • Mappings: tick both AZs offered (typically us-east-1a and us-east-1c); for each AZ choose the public subnet (Lab 1 named them archadv-<you>-public-a / archadv-<you>-public-c).
  • Security groups: Create new security group (opens a new tab):
    • Name: archadv-<you>-lab11-alb-sg
    • VPC: Lab 1 VPC
    • Inbound: type HTTP, source Anywhere-IPv4 (0.0.0.0/0).
    • Outbound: leave the default alone.
    • Create security group, return to the ALB tab, refresh the SG dropdown, pick the new SG, remove the default SG.
  • Listeners and routing:
    • Protocol HTTP, Port 80.
    • Default action: Create target group (opens a new tab):
      • Target type: Instances
      • Name: archadv-<you>-lab11-tg
      • Protocol HTTP, Port 80, VPC = Lab 1 VPC, Protocol version HTTP1.
      • Health check path: / (default).
      • Next, do not register any targets (the ASG will), Create target group, return to the ALB tab, refresh, pick this target group.
  • Click Create load balancer. State will be provisioning; continue with Step 3 while it works.

Now wire the ASG SG to allow traffic from the ALB SG:

  • Navigate: EC2 → Security Groups → archadv-<you>-lab11-asg-sg → Inbound rules → Edit inbound rules.
  • Add rule: type HTTP, source Custom → start typing archadv-<you>-lab11-alb-sg in the search box, pick that SG (you should be picking an sg-... ID, not a CIDR).
  • Save rules.

3. Auto Scaling Group (7 min)

  • Navigate: EC2 → Auto Scaling Groups → Create Auto Scaling group.
  • Step 1: Name archadv-<you>-lab11-asg; Launch template archadv-<you>-lab11-lt (Latest). Next.
  • Step 2 — Choose instance launch options:
    • VPC: Lab 1 VPC
    • Availability Zones and subnets: pick the same two public subnets the ALB uses (archadv-<you>-public-a and archadv-<you>-public-c). Using public subnets here means the EC2s reach SSM via the IGW directly — no NAT dependency.
    • Instance type requirements: leave defaults.
    • Next.
  • Step 3 — Integrate with other services:
    • Load balancing: Attach to an existing load balancer → Choose from your load balancer target groups → archadv-<you>-lab11-tg
    • Health checks: tick Turn on Elastic Load Balancing health checks.
    • Next.
  • Step 4 — Configure group size and scaling:
    • Desired capacity: 2
    • Min: 2, Max: 4
    • Scaling policy: Target tracking scaling policy
      • Scaling policy name: lab11-rcpt-target-tracking
      • Metric type: Application Load Balancer request count per target
      • Target group: archadv-<you>-lab11-tg
      • Target value: 10 (10 requests per target per minute — intentionally low so we can trigger it)
      • Instance warmup: 60 seconds
    • Next.
  • Step 5 — Add notifications: skip. Next.
  • Step 6 — Add tags: add Course = archadv and Owner = <you>. Tick Tag new instances. Next.
  • Step 7 — Review → Create Auto Scaling group.

Wait ~3 minutes. Refresh the ASG list until the Instances tab shows 2 instances and both report Lifecycle = InService, Health status = Healthy.

Then check EC2 → Target Groups → archadv-<you>-lab11-tg → Targets: 2 instances, Status = healthy. If status is unhealthy (Target.FailedHealthChecks), the user-data is still installing httpd — wait another 60 sec and refresh.

4. Validate baseline (2 min)

In CloudShell:

YOU=<you>
ALB=$(aws elbv2 describe-load-balancers \
  --names archadv-$YOU-lab11-alb \
  --query 'LoadBalancers[0].DNSName' --output text)
echo "ALB: $ALB"
for i in 1 2 3 4 5 6; do curl -s http://$ALB/; done

Expected: 6 lines of HTML, alternating between two different i-... instance IDs (round-robin).

Failure modes:

  • Could not resolve host → ALB still provisioning. Wait 60 sec and retry.
  • HTTP 503 → targets are unhealthy. Re-check Step 3 health box.
  • Always the same instance ID → only one target healthy. Wait for the second to pass health checks.

5. Generate load with curl and watch scale-up (7 min)

In CloudShell — this loop sends ~6,000 requests over 2 minutes. Apache Bench (ab) is not available on CloudShell without privileged install; a plain curl loop is fine to exceed the target-tracking threshold of 10 req/target/min:

# 2 minutes of sustained traffic, ~50 requests/sec
end=$(( $(date +%s) + 120 ))
while [ $(date +%s) -lt $end ]; do
  for i in $(seq 1 50); do
    curl -s -o /dev/null http://$ALB/ &
  done
  wait
done
echo "done"

While that runs, in a new browser tab:

  • Navigate CloudWatch → Metrics → All metrics → ApplicationELB → Per AppELB, per TG Metrics, locate the row where TargetGroup is your TG and metric is RequestCountPerTarget. Graph it. Statistic Sum, period 1 minute. You will see spikes well above 10.
  • Navigate EC2 → Auto Scaling Groups → archadv-<you>-lab11-asg → Activity tab. Within ~1–2 min of sustained load, a new row appears:
Successful — Launching a new EC2 instance: i-...
Cause: At <time> a monitor alarm
TargetTracking-archadv-<you>-lab11-asg-AlarmHigh-... in state ALARM
triggered policy lab11-rcpt-target-tracking, changing the desired
capacity from 2 to 3.

Refresh until the new instance reports InService (~3 min total). That's the lab outcome.

If no scaling activity appears after 4 min of load: the target value got typed as something other than 10 — edit the policy and recheck. Or your SG rule (Step 2 wire-up) didn't save and requests aren't reaching targets — check ALB HTTPCode_Target_2XX_Count.

Validation checklist

Discussion (5 min — instructor-led)

For each scenario, ask the room "would ALBRequestCountPerTarget work?":

  1. Spiky news site (90% reads, 50× spikes) — Yes. Request count IS saturation here.
  2. Internal HR app (idle off-hours) — Use scheduled scaling instead; you know the curve in advance.
  3. Real-time game backend (10K concurrent connections) — No. Scale on active connections, not requests.
  4. Batch image processing (SQS-driven) — No ALB at all. Scale on ApproximateNumberOfMessagesVisible.
  5. IoT telemetry to Kinesis — Kinesis IncomingRecords; for Lambda consumers, iterator age.

The durable lesson: scale on the metric that leads saturation. CPU lags for memory- or queue-bound workloads.

Cleanup

In this order, otherwise deletes block on dependencies:

  1. EC2 → Auto Scaling Groups → archadv-<you>-lab11-asg → Edit → set desired/min/max all to 0, wait for instances to terminate (~2 min), then Delete.
  2. EC2 → Load Balancers → tick the ALB → Delete.
  3. EC2 → Target Groups → tick the TG → Delete.
  4. EC2 → Launch Templates → tick the LT → Delete.
  5. EC2 → Security Groups → delete archadv-<you>-lab11-asg-sg THEN archadv-<you>-lab11-alb-sg (ASG SG references ALB SG, so delete in that order).

Do NOT delete the Lab 1 VPC, subnets, IGW, NAT, or routes. The capstone lab reuses them.

Stretch goals (only if you finish early)

  • Add a second scaling policy: target tracking on average CPU 50%. With httpd serving a static index, CPU stays low — demonstrating that the CPU policy doesn't fire while the request-count policy does.
