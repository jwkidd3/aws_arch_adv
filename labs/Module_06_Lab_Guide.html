Advanced Architecting on AWS

Lab 6 — Build & deploy a container on ECS Fargate

Objective

Build a container image, push it to ECR, then run it as an ECS Fargate service behind an Application Load Balancer. End with a rolling update so you see ECS draining old tasks while bringing up new ones.

Time budget: 50 minutes

Pre-flight

  1. Sign in to Sandbox<N>. Region us-east-1.
  2. You need a VPC with public + private subnets across 2 AZs and a NAT — reuse Lab 1's VPC. Do not use the default VPC — it has only public subnets, and Step 6 below requires private subnets with NAT for the Fargate tasks.
  3. Open CloudShell in us-east-1 (top-right toolbar). All build steps run here.

Steps

1. Create the ECR repository (2 min)

  • Amazon ECR → Repositories → Create repository
  • Name: archadv-<you>-hello
  • Image scanning: enable
  • Encryption: AES-256
  • Create.

Note the URI — looks like 123456789012.dkr.ecr.us-east-1.amazonaws.com/archadv-<you>-hello.

2. Build the image (CloudShell, 5 min)

In CloudShell:

mkdir -p hello && cd hello

cat > Dockerfile <<'EOF'
FROM public.ecr.aws/docker/library/nginx:1.27-alpine
RUN echo '<h1>archadv hello v1</h1>' > /usr/share/nginx/html/index.html
EOF

ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
REGION=us-east-1
REPO=$ACCOUNT.dkr.ecr.$REGION.amazonaws.com/archadv-<you>-hello

aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $ACCOUNT.dkr.ecr.$REGION.amazonaws.com
docker build -t archadv-hello:v1 .
docker tag archadv-hello:v1 $REPO:v1
docker push $REPO:v1

Replace <you> with your name throughout. The push should complete in 30–60 sec.

3. ECS cluster (1 min)

First-time ECS prep (one-time per Sandbox): the ECS service-linked role AWSServiceRoleForECS must exist before the first cluster create, or you get "Unable to assume the service linked role". Run this once in CloudShell:

aws iam create-service-linked-role --aws-service-name ecs.amazonaws.com

If you see InvalidInput: Service role already exists, that's fine — proceed.

  • Amazon ECS → Clusters → Create cluster
  • Name: archadv-<you>-cluster
  • Infrastructure: AWS Fargate (serverless)
  • Create. (Cluster is empty until you add a service.)

4. Task definition (3 min)

  • ECS → Task definitions → Create new task definition
  • Family: archadv-<you>-hello
  • Launch type: Fargate
  • OS, architecture: Linux/X86_64
  • CPU: 0.25 vCPU, Memory: 0.5 GB
  • Task role: leave blank
  • Task execution role: Create new (will be created with AmazonECSTaskExecutionRolePolicy)
  • Container:
    • Name: web
    • Image URI: <account>.dkr.ecr.us-east-1.amazonaws.com/archadv-<you>-hello:v1
    • Port: 80 (TCP)
  • Create.

5. Application Load Balancer (5 min)

  • EC2 → Load Balancers → Create load balancer → Application
  • Name: archadv-<you>-alb
  • Scheme: internet-facing
  • VPC: the Lab 1 VPC (the one with private subnets — not the default VPC)
  • Mappings: 2 AZs, public subnets in each
  • Security group: new — allow 80/tcp from 0.0.0.0/0
  • Listener: HTTP:80
  • Target group: Create target group in a new tab:
    • Type: IP addresses
    • Name: archadv-<you>-tg
    • Protocol: HTTP, port 80
    • VPC: same
    • Health check path: /
    • Click Next.
    • Register targets page: leave the IP list EMPTY. Do not enter any IP address. The ECS service in step 6 will register Fargate task IPs automatically. Click Create target group.
  • Back in the ALB tab, refresh and select the new target group as the default action.
  • Create the ALB. Wait ~2 min until state Active.

6. ECS service (3 min)

Before you start: you will need the ALB security group ID (the SG you created in step 5, named like archadv-<you>-alb-sg). Open it in another tab now: EC2 → Security Groups → filter on archadv-<you> → copy the sg-... ID for the ALB SG. You will paste it into the inbound source field below.

  • Navigate: Amazon ECS → Clusters → click archadv-<you>-cluster → Services tab → Create.
  • Environment section:
    • Existing cluster: archadv-<you>-cluster (pre-filled).
    • Compute configuration (advanced): Launch type.
    • Launch type: FARGATE.
    • Platform version: LATEST.
  • Deployment configuration section:
    • Application type: Service.
    • Task definition family: archadv-<you>-hello.
    • Revision: the highest number (it will be 1 on first run).
    • Service name: archadv-<you>-hello-svc.
    • Service type: Replica.
    • Desired tasks: 2.
  • Networking section:
    • VPC: select the Lab 1 VPC by name (it is the VPC tagged Course=archadv). Do NOT pick the default VPC — its subnets are all public and have no NAT, so the tasks will fail to pull the image.
    • Subnets: remove all 4 default-selected subnets first, then add ONLY the 2 private subnets from the Lab 1 VPC. Use the table below to identify them.
    #Subnet name tagAdd?Why
    1archadv-public-1aNOPublic — would give task a route via IGW; we want NAT-only egress
    2archadv-public-1bNOSame as above
    3archadv-private-1aYESPrivate subnet in AZ us-east-1a
    4archadv-private-1bYESPrivate subnet in AZ us-east-1b
    • Security group: select Create a new security group.
      • Security group name: archadv-<you>-tasks-sg.
      • Description: ECS Fargate tasks — accept 80 from ALB SG only.
      • Inbound rules — add exactly one rule:
        #TypeProtocolPortSource typeSource value
        1Custom TCPTCP80Customthe ALB SG ID you copied above (paste the sg-...)
      • Outbound rules: leave the default rule alone (the wizard pre-populates "All traffic to 0.0.0.0/0" — this is correct; do not add or remove anything).
    • Public IP: TURNED OFF (toggle to off). Tasks reach ECR and the internet via the NAT Gateway in the Lab 1 VPC.
  • Load balancing section:
    • Use load balancing: checked.
    • Load balancer type: Application Load Balancer.
    • Container to load balance: web 80:80 (the wizard offers it because the task definition exposes port 80).
    • Application Load Balancer: Use an existing load balancer.
    • Load balancer name: archadv-<you>-alb.
    • Listener: Use an existing listener → 80:HTTP.
    • Target group: Use an existing target group → archadv-<you>-tg.
    • Health check grace period: 60 seconds.
  • Leave all other sections at defaults. Click Create.
  • Wait for the service to converge. On the service's Tasks tab, success looks like: 2 rows, both with Last status: RUNNING, Health status: HEALTHY, takes 2–4 min.
  • Failure modes to watch for:
    • Tasks loop PROVISIONING → DEPROVISIONING: networking is wrong — almost always a public subnet was selected. Re-check the subnet table above.
    • Tasks reach RUNNING but target group shows unhealthy: SG rule on the task SG is missing or pointing at the wrong source. Confirm the inbound rule references the ALB SG ID, not 0.0.0.0/0.
    • Tasks fail with CannotPullContainerError: NAT Gateway is missing/route table not associated. Open the Lab 1 VPC → Route Tables → confirm the private subnets' route table has 0.0.0.0/0 → nat-....

7. Validate (2 min)

In CloudShell — replace <you> in the command with your name slug:

ALB=$(aws elbv2 describe-load-balancers --names archadv-<you>-alb --query 'LoadBalancers[0].DNSName' --output text)
echo $ALB     # sanity-check: should print a hostname ending in .elb.amazonaws.com
curl -i http://$ALB

Success looks like:

  • HTTP status 200 OK on the first line of output.
  • Body is exactly <h1>archadv hello v1</h1>.

Failure modes:

  • curl: (52) Empty reply from server or 503 Service Unavailable: targets are not healthy yet. Go to EC2 → Target Groups → archadv-<you>-tg → Targets tab — wait until both rows show Health status: healthy. Can take 60–90 sec after tasks reach RUNNING.
  • Could not resolve host: the ALB variable is empty. Re-run the describe-load-balancers line and check you used your actual name slug.

8. Rolling update (5 min)

Step 8a — build and push v2 in CloudShell. Re-use the same shell from step 2 (the $ACCOUNT, $REGION, $REPO env vars must still be set; if the session timed out, re-export them first):

cd ~/hello
sed -i 's/v1/v2/' Dockerfile
docker build -t archadv-hello:v2 .
docker tag archadv-hello:v2 $REPO:v2
docker push $REPO:v2

Success looks like: docker push ends with a line containing v2: digest: sha256:... and the new tag is visible at Amazon ECR → Repositories → archadv-<you>-hello → Images.

Step 8b — create a new task-definition revision (console).

  • Navigate: Amazon ECS → Task definitions → click archadv-<you>-hello → select the row with the highest revision number → Actions → Create new revision → Create new revision.
  • Scroll to the Container - 1 section.
  • Find the Image URI field. Change ONLY the trailing tag: :v1 → :v2. The account ID, region, and repo name stay the same. Example before/after:
    • Before: 123456789012.dkr.ecr.us-east-1.amazonaws.com/archadv-<you>-hello:v1
    • After: 123456789012.dkr.ecr.us-east-1.amazonaws.com/archadv-<you>-hello:v2
  • Do NOT change anything else.
  • Scroll to the bottom → Create. A new revision (2) appears.

Step 8c — point the service at the new revision.

  • Navigate: Amazon ECS → Clusters → archadv-<you>-cluster → Services tab → click archadv-<you>-hello-svc → Update service.
  • Revision: change from 1 (LATEST) to 2 (LATEST).
  • Force new deployment: leave UNCHECKED (the revision change alone triggers the rollout).
  • Leave every other field alone. Scroll down → Update.

Step 8d — observe the rollout. Open a fresh CloudShell tab and start a 1-per-second curl loop BEFORE the new tasks come up. Replace <you>:

ALB=$(aws elbv2 describe-load-balancers --names archadv-<you>-alb --query 'LoadBalancers[0].DNSName' --output text)
while true; do curl -s http://$ALB; sleep 1; done

In the console, watch Service → Tasks tab. Expected timeline (3–5 min total):

  1. 2 new tasks appear in PROVISIONING, then PENDING, then RUNNING.
  2. Once both new tasks are HEALTHY in the target group, the 2 old tasks transition to DEACTIVATING → STOPPING → STOPPED.
  3. Briefly there are 4 tasks (200% deployment) — this is correct.

Success looks like: the curl loop output flips from <h1>archadv hello v1</h1> to <h1>archadv hello v2</h1> with zero non-200 responses and zero empty lines. Stop the loop with Ctrl-C.

Failure modes:

  • Curl loop returns 504 or empty during rollout: minimum healthy percent is too low. Skip — this is just a flake; rerun.
  • Rollout stalls with 2 new tasks stuck UNHEALTHY: check that the new image was actually pushed (aws ecr describe-images --repository-name archadv-<you>-hello should list v2).

Validation checklist

Cleanup

  1. ECS service → Update → desired tasks 0, then Delete.
  2. ECS cluster → Delete.
  3. ALB → Delete. Target group → Delete.
  4. ECR repository → Delete (and image scan results).
  5. Task execution role → Delete.

Stretch goals

  • Add Container Insights to the cluster and inspect a task's CPU and memory metrics during the rolling update.
  • Switch the ALB listener to HTTPS:443 with an ACM-issued certificate (you'll need a Route 53 hosted zone you control or DNS validation through email — instructor-provided).
  • Add an ECS service auto-scaling policy (target tracking on CPU 50%) and trigger it with ab from CloudShell.
