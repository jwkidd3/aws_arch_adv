Advanced Architecting on AWS

Lab 8 — ALB + ASG + WAF

Objective

Build a horizontally-scaled web tier (ALB + ASG) and protect it with AWS WAF using AWS-managed rule groups + a custom rate-based rule. Then validate by triggering a SQLi-shape request and a brute-force loop.

Time budget: 50 minutes

Pre-flight

  1. Sign in to Sandbox<N>. Region us-east-1.
  2. Use the Lab 1 VPC (the one tagged Course=archadv, with 2 public + 2 private subnets and a NAT Gateway). Do not use the default VPC — its subnets are all public, so step 3 (ASG in private subnets) will fail.
  3. Confirm the EC2 SSM IAM instance profile exists from earlier labs: IAM → Roles → search for a role named archadv-ssm-ec2-role or similar with AmazonSSMManagedInstanceCore attached. If missing, create it now: trusted entity AWS service → EC2, attach AmazonSSMManagedInstanceCore, name it archadv-<you>-ssm-ec2-role. (No iam:PassRole issues — your Sandbox IdC role has admin.)
  4. Open CloudShell in us-east-1.

Known capacity quirk: t3.micro in us-east-1b occasionally returns InsufficientInstanceCapacity. If the ASG cannot launch in step 3, edit the ASG and remove us-east-1b from subnets (use us-east-1a + us-east-1c instead). The capstone runs fine with 2 AZs in any combination.

Steps

1. Launch template (5 min)

  • Navigate: EC2 → Launch templates → Create launch template.
  • Launch template name and description section:
    • Launch template name: archadv-<you>-lt.
    • Template version description: v1 - httpd with instance ID.
    • Auto Scaling guidance: tick "Provide guidance to help me set up a template that I can use with EC2 Auto Scaling" — this hides ASG-incompatible fields.
  • Application and OS Images (AMI) section:
    • Quick Start tab → Amazon Linux → AMI dropdown: pick the row labeled Amazon Linux 2023 AMI with the green "Free tier eligible" tag and architecture 64-bit (x86). (Do NOT pick the Arm64 row — the user-data below assumes dnf on x86_64; Arm64 works too but the AMI ID changes.)
  • Instance type section: t3.micro.
  • Key pair (login) section: Don't include in launch template. (Course rule: SSM Session Manager only — no SSH, no key pairs, no port 22.)
  • Network settings section:
    • Subnet: Don't include in launch template (the ASG sets the subnet).
    • Firewall (security groups): Create security group.
      • Security group name: archadv-<you>-ec2-sg.
      • Description: EC2 web tier — accept 80 from ALB SG only.
      • VPC: the Lab 1 VPC (NOT default).
      • Inbound rules: leave empty for now. You will add the rule in step 2 after the ALB SG exists. (Adding it now creates a chicken-and-egg loop — the ALB SG does not exist yet.)
  • Advanced details section (expand):
    • IAM instance profile: archadv-<you>-ssm-ec2-role (the role from pre-flight step 3).
    • Metadata version: V2 only (token required).
    • Metadata response hop limit: 2.
    • User data: paste this verbatim (the metadata IMDSv2 token fetch matches the V2-only setting): 
      #!/bin/bash
dnf install -y httpd
systemctl enable --now httpd
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
HOST=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id)
echo "<h1>archadv $HOST</h1>" > /var/www/html/index.html
  • Resource tags (optional): Course=archadv, Owner=<you>. Apply to: Instances.
  • Click Create launch template.

Success looks like: the template list shows version 1 as Default version. Click into it and verify the Advanced details tab shows IMDSv2 = Required and the user data preview matches.

2. Application Load Balancer + target group (7 min)

You will create the ALB first (which creates the ALB SG), then go back and add the inbound rule on the EC2 SG that references the new ALB SG.

Step 2a — create the target group.

  • Navigate: EC2 → Target groups → Create target group.
  • Choose a target type: Instances.
  • Target group name: archadv-<you>-tg.
  • Protocol: HTTP. Port: 80.
  • IP address type: IPv4.
  • VPC: the Lab 1 VPC.
  • Protocol version: HTTP1.
  • Health checks: protocol HTTP, path /.
  • Advanced health check settings (expand): leave all defaults (port: traffic port, healthy threshold 5, unhealthy threshold 2, timeout 5 sec, interval 30 sec).
  • Next → register targets page: leave the instance list EMPTY. The ASG in step 3 registers instances automatically.
  • Create target group.

Step 2b — create the ALB.

  • Navigate: EC2 → Load balancers → Create load balancer → Application Load Balancer → Create.
  • Basic configuration:
    • Load balancer name: archadv-<you>-alb.
    • Scheme: Internet-facing.
    • IP address type: IPv4.
  • Network mapping:
    • VPC: the Lab 1 VPC.
    • Mappings — pick exactly 2 AZs and 2 public subnets:
      AZSubnet to pick
      us-east-1aarchadv-public-1a
      us-east-1barchadv-public-1b
      Do NOT select the private subnets — ALB nodes need IGW egress to be internet-facing.
  • Security groups:
    • Click Create new security group (opens in new tab).
    • Security group name: archadv-<you>-alb-sg.
    • Description: ALB - accept HTTP from internet.
    • VPC: Lab 1 VPC.
    • Inbound rules — add exactly one:
      #TypeSource
      1HTTP (80)Anywhere-IPv4 (0.0.0.0/0)
    • Outbound rules: leave the default rule alone.
    • Create security group. Note the resulting sg-... ID.
    • Back in the ALB tab, click the refresh icon next to Security groups and select archadv-<you>-alb-sg. Remove the default SG from the selection if it auto-added.
  • Listeners and routing:
    • Protocol: HTTP. Port: 80.
    • Default action: Forward to target group → archadv-<you>-tg.
  • Create load balancer. Wait ~2 min on the LB details page until State: Active.

Step 2c — add the EC2 SG inbound rule (now that the ALB SG exists).

  • Navigate: EC2 → Security groups → click archadv-<you>-ec2-sg.
  • Inbound rules tab → Edit inbound rules.
  • Click Add rule. Set exactly:
    FieldValue
    TypeHTTP (auto-fills protocol TCP, port 80)
    Source typeCustom
    Sourcestart typing archadv-<you>-alb-sg and click the matching sg-... result
    DescriptionFrom ALB
  • Save rules. Outbound rules: do not touch.

3. Auto Scaling Group (7 min)

  • Navigate: EC2 → Auto Scaling Groups → Create Auto Scaling group.
  • Step 1 — Choose launch template:
    • Auto Scaling group name: archadv-<you>-asg.
    • Launch template: archadv-<you>-lt. Version: Default (1).
    • Click Next.
  • Step 2 — Choose instance launch options:
    • Instance type requirements: Override launch template → instance types: add t3.micro, t3.small, t3a.micro. (Multiple types help dodge the us-east-1b capacity issue.)
    • Instance purchase options: 100% On-Demand (default).
    • Network → VPC: Lab 1 VPC.
    • Availability Zones and subnets: select exactly 2 private subnets:
      AZSubnet to pick
      us-east-1aarchadv-private-1a
      us-east-1barchadv-private-1b
      (If you hit InsufficientInstanceCapacity later, swap 1b for 1c as called out in the pre-flight quirk box.)
    • Next.
  • Step 3 — Configure advanced options:
    • Load balancing: Attach to an existing load balancer.
    • Choose target groups: archadv-<you>-tg | HTTP.
    • VPC Lattice integration options: No VPC Lattice service.
    • Health checks: Turn on Elastic Load Balancing health checks (this is the key change — ELB health beats EC2-only health for web tiers). Health check grace period: 120 seconds.
    • Additional settings: Enable group metrics collection within CloudWatch.
    • Next.
  • Step 4 — Configure group size and scaling:
    • Desired capacity: 2.
    • Min: 2. Max: 4.
    • Scaling policies: Target tracking scaling policy.
      • Policy name: archadv-cpu50.
      • Metric type: Average CPU utilization.
      • Target value: 50.
      • Instance warmup: 120 seconds.
    • Instance scale-in protection: off.
    • Next → Next → Create Auto Scaling group.

Watch the Activity tab. Success looks like: 2 instances move from Pending → InService within 3 min. On EC2 → Target groups → archadv-<you>-tg → Targets, both targets show Health status: healthy within ~90 sec after that (the user-data installs httpd before the health check passes).

Failure modes:

  • Activity log shows Launching a new EC2 instance ... failed: InsufficientInstanceCapacity: edit the ASG → Network → swap us-east-1b subnet for us-east-1c → save. The ASG will retry within 5 min automatically.
  • Targets stuck unhealthy: SSM into one instance to debug. EC2 → Instances → pick the instance → Connect → Session Manager → Connect. Run systemctl status httpd and curl -s localhost. If httpd never started, user-data did not run — the AMI was wrong (Arm64 selected instead of x86_64).

4. Validate the baseline (2 min)

In CloudShell — replace <you>:

ALB=$(aws elbv2 describe-load-balancers --names archadv-<you>-alb --query 'LoadBalancers[0].DNSName' --output text)
echo $ALB
for i in 1 2 3 4 5 6 7 8; do curl -s http://$ALB; done

Success looks like: 8 lines of <h1>archadv i-...</h1> with exactly 2 distinct instance IDs alternating (the ALB does round-robin by default).

Failure mode: all 8 lines are the same instance — the other target is unhealthy. Check the Target group's Targets tab.

5. AWS WAF web ACL (12 min)

  • Navigate: AWS WAF & Shield → Web ACLs. Region selector top-right: US East (N. Virginia) (regional WAF must match the ALB region).
  • Click Create web ACL.

Step 5a — Describe web ACL and associate it.

  • Resource type: Regional resources (Application Load Balancer, API Gateway, ...). NOT "CloudFront distributions".
  • Region: US East (N. Virginia).
  • Name: archadv-<you>-waf.
  • CloudWatch metric name: auto (accept).
  • Description: leave blank.
  • Associated AWS resources: click Add AWS resources → tick Application Load Balancer → tick the row for archadv-<you>-alb → Add.
  • Next.

Step 5b — Add rules and rule groups. Click Add rules → Add managed rule groups. Under AWS managed rule groups, expand the list and toggle these 3 rule groups ON in this order (priority is set by add-order — top is highest priority, evaluated first):

PriorityRule group (verbatim console name)VendorWhy
1Core rule set (AWSManagedRulesCommonRuleSet)AWSGeneric OWASP top-10 protection
2Known bad inputs (AWSManagedRulesKnownBadInputsRuleSet)AWSCatches known exploit payloads (Log4Shell, etc.)
3SQL database (AWSManagedRulesSQLiRuleSet)AWSTrips on the probe in step 6

For each of the 3 rule groups, expand the toggle and check the Set rules action to block checkbox under Override all rule actions. This is critical:

Why "Override all rule actions to Block": several rules inside the Core rule set default to Count (observe only), not Block. If you skip the override, your SQLi probe in step 6 will return 200 OK instead of 403, the rule will show up in Sampled requests as COUNT, and the lab will appear broken. Tick the Block override on all 3 rule groups.

  • Click Add rules (bottom of the rule-groups panel) — you return to the rules list with 3 entries.
  • Default web ACL action for requests that don't match any rules: Allow.
  • Next.

Step 5c — Set rule priority. Order of the 3 rule groups: Core rule set → Known bad inputs → SQL database (drag to reorder if needed). Click Next.

Step 5d — Configure metrics. Accept all defaults (CloudWatch metrics on for each rule + ACL-level). Next.

Step 5e — Review and create. Create web ACL. Wait ~30 sec; the association with the ALB takes effect within a minute.

6. Trigger a managed-rule block (3 min)

In CloudShell — the literal-string single-quotes inside the URL are intentional (they form the SQLi pattern):

ALB=$(aws elbv2 describe-load-balancers --names archadv-<you>-alb --query 'LoadBalancers[0].DNSName' --output text)
curl -i "http://$ALB/?id=1%27%20OR%20%271%27=%271"

Success looks like: first line of response is HTTP/1.1 403 Forbidden and the body contains <TITLE>ERROR: The request could not be satisfied</TITLE>.

Then navigate: AWS WAF → Web ACLs → archadv-<you>-waf → Sampled requests tab. Within 2 min the request appears with:

  • Action: BLOCK (red).
  • Matching rule: AWSManagedRulesSQLiRuleSet (or a CRS sub-rule that matched first).

Failure modes:

  • 200 OK instead of 403: you skipped the Override all rule actions to Block checkbox in step 5b. Edit the web ACL, expand each rule group, tick the override, save.
  • Sampled requests is empty: WAF samples are best-effort and lag up to 5 min. Refresh; if still empty, check the request was sent to the correct ALB DNS.

7. Custom rate-based rule (12 min)

Step 7a — add the rule.

  • Navigate: AWS WAF → Web ACLs → archadv-<you>-waf → Rules tab → Add rules → Add my own rules and rule groups.
  • Rule type: Rule builder.
  • Name: archadv-rate-limit.
  • Type: Rate-based rule.
  • Rate limit: 100.
  • Evaluation window: 1 minute. (NOT the default 5 min — the 1-minute window trips faster from CloudShell, which matters because CloudShell egresses through a small NAT IP pool that AWS may share across sessions.)
  • Request aggregation: Source IP.
  • Scope of inspection and rate limiting: Consider all requests.
  • Action: Block.
  • Click Add rule → Save. Priority order: keep archadv-rate-limit at the bottom (priority 4) — the managed rule groups should still run first so SQLi/CRS bans get specific labels.

Step 7b — trigger the rule from CloudShell. WAF rate-based rules group requests by source IP. CloudShell sessions in us-east-1 egress from a NAT pool — sometimes 2 students in the same class share an outbound IP, which means their request rates aggregate. The 1-minute / 100-request window above is tuned to trip reliably even at single-user pace.

# Hammer the ALB with ~250 requests as fast as possible (parallel with xargs)
ALB=$(aws elbv2 describe-load-balancers --names archadv-<you>-alb --query 'LoadBalancers[0].DNSName' --output text)
seq 1 250 | xargs -n1 -P20 -I{} curl -s -o /dev/null -w "%{http_code}\n" http://$ALB/ \
  | sort | uniq -c

Success looks like output similar to:

     97 200
    153 403

(The first ~100 in the 1-min window pass with 200, the rest hit the rate rule and return 403.)

Failure modes:

  • All 250 return 200: the rate rule has not propagated yet. WAF rule changes can take 30–60 sec to be live globally. Wait 1 minute and re-run.
  • Output is all 200 even after waiting: the rule was added at the wrong scope. Open archadv-<you>-waf → Rules → archadv-rate-limit → Edit and confirm Action = Block (not Count). The default for new rate rules in some console versions is Count.
  • Curl is too slow to trip 100 req/min: increase parallelism with -P40.

Step 7c — confirm in CloudWatch.

  • Navigate: CloudWatch → Metrics → All metrics → AWS/WAFV2 → Region, Rule, WebACL.
  • Filter on WebACL = archadv-<you>-waf and Rule = archadv-rate-limit. Plot the BlockedRequests metric. Sum, 1-minute period.
  • Success looks like: a spike of ~150 in the minute you ran the loop.

Validation checklist

Cleanup

  1. WAF: archadv-<you>-waf → Associated AWS resources → disassociate the ALB, then Delete web ACL.
  2. ASG: EC2 → Auto Scaling Groups → archadv-<you>-asg → Edit → set desired/min/max all to 0 → wait for 0 instances (~2 min) → back → Delete.
  3. Launch template: EC2 → Launch templates → archadv-<you>-lt → Actions → Delete template.
  4. ALB: EC2 → Load balancers → archadv-<you>-alb → Actions → Delete load balancer. Wait until gone, then delete target group archadv-<you>-tg.
  5. Security groups: delete archadv-<you>-ec2-sg first, then archadv-<you>-alb-sg (the EC2 SG references the ALB SG; if you delete the ALB SG first the EC2 SG delete will fail).
  6. IAM: leave archadv-<you>-ssm-ec2-role in place — it is reused in Lab 9.

Stretch goals

  • Add an AWS Shield Advanced subscription discussion (do NOT enable it — $3,000/mo). Look at the Shield protections summary page.
  • Add a CloudFront distribution in front of the ALB and re-test. WAF should now be associated with the CloudFront distribution (global) instead of the ALB (regional).
  • Set the WAF rules to Count instead of Block for one day in production. Why? (Answer: you observe what would be blocked before going hot. Most teams skip this and regret it.)
