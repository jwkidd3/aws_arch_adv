Advanced Architecting on AWS

Lab 9 — KMS + Secrets Manager

Objective

Create a customer-managed KMS key, encrypt an S3 object with it, then store and manually rotate a database password in Secrets Manager. Practice the key policy as the source of truth mental model.

Time budget: 50 minutes

Throughout this lab, replace <you> with your assigned student slug (e.g., mary-smith). All work is in us-east-1.

Pre-flight

  1. Sign in to Sandbox<N> via the IAM Identity Center access portal. Confirm the role badge top-right reads AWSAdministratorAccess @ Sandbox<N>.
  2. Top-right region selector: US East (N. Virginia) us-east-1.
  3. Open CloudShell (icon in the top bar). Wait for the prompt.

Part A — Customer-managed KMS key (15 min)

1. Create the CMK (5 min)

  • Navigate: Key Management Service (KMS) → Customer managed keys → Create key.
  • Step 1 — Configure key:
    • Key type: Symmetric
    • Key usage: Encrypt and decrypt
    • Leave Advanced options at defaults. Next.
  • Step 2 — Add labels:
    • Alias: archadv-<you>-key
    • Description: archadv lab key
    • Tags: add Course = archadv and Owner = <you>. Next.
  • Step 3 — Key administrators: tick the role that starts with AWSReservedSSO_AWSAdministratorAccess_ (the IdC role you signed in with). Leave Allow key administrators to delete this key ticked. Next.
  • Step 4 — Define key usage permissions: tick the same AWSReservedSSO_AWSAdministratorAccess_ role. Next.
  • Step 5 — Review: skim the auto-generated key policy. Note four statement Sids: Enable IAM User Permissions, Allow access for Key Administrators, Allow use of the key, Allow attachment of persistent resources. Click Finish.

Validation: the new key shows in the table with status Enabled and your alias. If you see "You don't have permission," your IdC session expired — sign out and back in.

2. Create the S3 bucket and default encryption (3 min)

  • Navigate: S3 → Create bucket.
  • Bucket name: archadv-<you>-secure
  • AWS Region: US East (N. Virginia) us-east-1.
  • Object Ownership: ACLs disabled (recommended) (default — leave it).
  • Block Public Access: Block all public access (default — leave it).
  • Default encryption:
    • Encryption type: Server-side encryption with AWS Key Management Service keys (SSE-KMS)
    • AWS KMS key: Choose from your AWS KMS keys → pick alias/archadv-<you>-key
    • Bucket Key: Enable (leave as default — this is the production setting and works fine for this lab).
  • Click Create bucket.

3. Upload an encrypted object (3 min)

In CloudShell:

YOU=<you>    # e.g. mary-smith
echo "secret-payload-$(date +%s)" > /tmp/secret.txt
aws s3 cp /tmp/secret.txt s3://archadv-$YOU-secure/
aws s3api head-object --bucket archadv-$YOU-secure --key secret.txt \
  --query '{SSE:ServerSideEncryption,KeyId:SSEKMSKeyId,BucketKey:BucketKeyEnabled}'

Expected output:

{
    "SSE": "aws:kms",
    "KeyId": "arn:aws:kms:us-east-1:...:key/...",
    "BucketKey": true
}

Failure modes:

  • SSE is AES256 → the default-encryption setting didn't save. Re-edit the bucket's Properties → Default encryption.
  • NoSuchBucket → typo in $YOU; bucket name is global and case-sensitive lowercase.

4. Find the KMS call in CloudTrail (4 min)

  • Navigate: CloudTrail → Event history.
  • Lookup attribute: Event name → value GenerateDataKey. Time range: Last 15 minutes.
  • Click into the most recent event. In the Event record JSON, locate:
    • requestParameters.keyId → matches your CMK ARN
    • requestParameters.encryptionContext.aws:s3:arn → references your bucket (Bucket Key uses the bucket ARN here)
    • userIdentity.sessionContext.sessionIssuer.userName → the AWSReservedSSO_AWSAdministratorAccess_ role

This is the encryption context mechanism — S3 tells KMS "this data key is for this bucket," and KMS records that on every call.

If the event isn't there yet: CloudTrail Event history lags 1–5 min. Refresh after 60 sec.

Part B — Secrets Manager (20 min)

1. Create the secret (5 min)

  • Navigate: AWS Secrets Manager → Secrets → Store a new secret.
  • Step 1 — Choose secret type:
    • Secret type: Other type of secret
    • Key/value pairs (use the Plaintext tab if easier; the form below pastes there directly):
    {"username":"archadvuser","password":"CHANGE-ME-AT-STEP-3"}
    • Encryption key: pick alias/archadv-<you>-key (your CMK from Part A).
    • Next.
  • Step 2 — Configure secret:
    • Secret name: archadv-<you>-db-pass
    • Description: archadv lab secret
    • Tags: Course = archadv, Owner = <you>
    • Next.
  • Step 3 — Configure rotation: leave Automatic rotation toggled off. Next.
  • Step 4 — Review: Store.

2. Read the secret via CLI (3 min)

In CloudShell:

aws secretsmanager get-secret-value \
  --secret-id archadv-$YOU-db-pass \
  --query SecretString --output text

Expected: a JSON string containing "username":"archadvuser" and "password":"CHANGE-ME-AT-STEP-3".

This succeeded because both policies allowed it: your IdC role has secretsmanager:GetSecretValue (IAM), AND the CMK's key policy allows kms:Decrypt for the same role. Remove either and this call fails — that's the "key policy as source of truth" takeaway.

3. Rotate manually (staging labels) (7 min)

Manual rotation is what students should learn — it's the mechanism. Automatic rotation via Lambda is production hygiene that lives in the rotation-Lambda hands-on lab (not this one).

  • Navigate: Secrets Manager → archadv-<you>-db-pass → Overview tab → Secret value → Retrieve secret value → Edit.
  • In the Key/value editor change the password value to ROTATED-VALUE-1.
  • Click Save.
  • Re-run the CLI from Step 2. password now reads ROTATED-VALUE-1.
  • Switch to the Versions tab on the secret. You see two rows:
    • New version → staging label AWSCURRENT
    • Old version → staging label AWSPREVIOUS

That two-version rollback window is the durable concept — same mechanic that automatic rotation uses, just done by hand here.

4. Rollback (3 min)

Real rotations fail. Practice rolling back to AWSPREVIOUS via CLI:

# Get the two version IDs
aws secretsmanager list-secret-version-ids \
  --secret-id archadv-$YOU-db-pass \
  --query 'Versions[].{Id:VersionId,Stages:VersionStages}'

# Capture the previous version ID into a variable
PREV=$(aws secretsmanager list-secret-version-ids \
  --secret-id archadv-$YOU-db-pass \
  --query 'Versions[?contains(VersionStages, `AWSPREVIOUS`)].VersionId | [0]' \
  --output text)

# Get the new version ID
CURR=$(aws secretsmanager list-secret-version-ids \
  --secret-id archadv-$YOU-db-pass \
  --query 'Versions[?contains(VersionStages, `AWSCURRENT`)].VersionId | [0]' \
  --output text)

# Swap the AWSCURRENT label back to the older version
aws secretsmanager update-secret-version-stage \
  --secret-id archadv-$YOU-db-pass \
  --version-stage AWSCURRENT \
  --move-to-version-id $PREV \
  --remove-from-version-id $CURR

# Confirm
aws secretsmanager get-secret-value --secret-id archadv-$YOU-db-pass \
  --query SecretString --output text

Expected: password is back to CHANGE-ME-AT-STEP-3. Staging label AWSCURRENT moved; no new secret version was created.

Part C — Key policy vs IAM policy (5 min, instructor-led discussion)

The instructor walks the room through one mental model:

  • IAM policy on a principal says "this role can call kms:Decrypt on key X."
  • Key policy on the CMK says "key X allows kms:Decrypt from this principal."
  • Both must say yes. If only one says yes, the call fails. That's why the saying goes: the key policy is the source of truth — it's the one most teams forget to check.
  • Cross-account: the key policy in the key's home account must name the foreign-account principal explicitly. IAM policy on the foreign side is not enough.

Validation checklist

Cleanup

  1. Secrets Manager → archadv-<you>-db-pass → Actions → Delete secret → set waiting period to 7 days (minimum). The secret is scheduled, not immediately gone.
  2. S3 → archadv-<you>-secure → Empty, then Delete.
  3. KMS → Customer managed keys → archadv-<you>-key → Key actions → Schedule key deletion → waiting period 7 days. The 7-day minimum is by design — keys can be restored within that window.

Stretch goals (only if you finish early)

  • Enable automatic annual key rotation on the CMK (Key actions → Enable key rotation). AWS rotates the key material; the ARN and alias stay the same.
  • Read your CMK's policy JSON in Key policy → Switch to policy view. Identify which of the four statements would be the single point of failure if removed.
