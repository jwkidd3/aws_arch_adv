Advanced Architecting on AWS

Lab 7 — CodePipeline → CodeBuild → CodeDeploy

Objective

Wire an AWS-native CI/CD pipeline that builds a new container image and deploys it to the ECS service from Lab 6. Then switch the deploy strategy from rolling to canary and watch traffic split.

Time budget: 65 minutes

Pre-flight

  1. Sign in to Sandbox<N>. Region us-east-1 (the same region as Lab 6 — CodePipeline source/build/deploy must all share a region).
  2. The ECS service archadv-<you>-hello-svc from Lab 6 must still be running with 2 healthy tasks. Confirm: Amazon ECS → Clusters → archadv-<you>-cluster → Services — service rolling count must show 2/2 Running. If you cleaned it up, redo Lab 6 steps 1–7 quickly first (skip the rolling update).
  3. Open CloudShell in us-east-1.
  4. Have your account ID ready (top-right corner of the console; 12 digits). You will paste it as an environment variable.

Source-control choice — read this first. AWS stopped onboarding new customers to CodeCommit in July 2024. AWS Organizations accounts created after that date cannot create CodeCommit repositories — the console shows "This service is not available" or you get an AccessDeniedException. The primary path in this lab uses GitHub + AWS CodeConnections, which works in every Sandbox in this course. A legacy CodeCommit path is preserved at the end as Appendix A for accounts that still have it enabled — if your instructor has not confirmed CodeCommit access, use the primary path.

Steps

1. Create the source repository on GitHub (5 min)

You need a personal GitHub account (free is fine). If you do not have one: https://github.com/signup — sign up, verify email, then come back. Total: 2 min.

Step 1a — create the empty repo on github.com.

  • Go to https://github.com/new.
  • Repository name: archadv-<you>-hello (e.g. archadv-jdoe-hello).
  • Visibility: Private.
  • Do NOT check "Add a README file", "Add .gitignore", or "Choose a license" — we want a truly empty repo (the wizard creates a usable initial commit).
  • Click Create repository.
  • On the next screen, copy the HTTPS clone URL — it looks like https://github.com/<your-gh-user>/archadv-<you>-hello.git.

Step 1b — create a fine-scoped GitHub Personal Access Token (PAT) so you can push from CloudShell.

  • Go to github.com → your avatar → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  • Token name: archadv-cloudshell.
  • Expiration: 7 days.
  • Resource owner: your own user.
  • Repository access: Only select repositories → pick archadv-<you>-hello.
  • Permissions → Repository permissions → Contents: Read and write. Leave everything else.
  • Generate token. Copy the github_pat_... value — you cannot view it again. Paste it into a scratch tab for the next step.

Step 1c — push the initial commit from CloudShell. Run these commands one at a time. Replace <you> with your name slug, <your-gh-user> with your GitHub username, and <PAT> with the fine-grained token from step 1b.

cd ~
git config --global user.name "<you>"
git config --global user.email "<you>@example.com"
git config --global init.defaultBranch main

# Clone empty repo using the PAT inline (one-shot; do not commit this URL anywhere)
git clone https://<your-gh-user>:<PAT>@github.com/<your-gh-user>/archadv-<you>-hello.git
cd archadv-<you>-hello

cat > Dockerfile <<'EOF'
FROM public.ecr.aws/docker/library/nginx:1.27-alpine
RUN echo '<h1>archadv hello pipeline v3</h1>' > /usr/share/nginx/html/index.html
EOF

cat > buildspec.yml <<'EOF'
version: 0.2
phases:
  pre_build:
    commands:
      - REPO=$AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/$IMAGE_REPO
      - aws ecr get-login-password --region $AWS_REGION | docker login --username AWS --password-stdin $AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com
  build:
    commands:
      - docker build -t $IMAGE_REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION .
      - docker tag $IMAGE_REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION $REPO:latest
      - docker push $REPO:latest
  post_build:
    commands:
      - printf '[{"name":"web","imageUri":"%s"}]' $REPO:latest > imagedefinitions.json
artifacts:
  files: imagedefinitions.json
EOF

git add Dockerfile buildspec.yml
git commit -m "init: Dockerfile + buildspec"
git push -u origin main

Success looks like: git push prints * [new branch] main -> main, and refreshing the GitHub repo page shows both files at the root.

Failure modes:

  • fatal: Authentication failed: PAT was pasted wrong or expired. Re-create in step 1b.
  • remote: Repository not found: PAT scope did not include this repo. Re-create the PAT with the correct Only select repositories choice.

1d. Create the CodeConnections connection to GitHub (3 min)

CodePipeline talks to GitHub through a CodeConnections (formerly CodeStar Connections) resource. You create it once and reuse it.

  • Navigate: Developer Tools → Settings → Connections. Direct URL: console.aws.amazon.com/codesuite/settings/connections.
  • Click Create connection.
  • Select a provider: GitHub.
  • Connection name: archadv-<you>-github.
  • Click Connect to GitHub — a popup opens to github.com.
  • In the popup: Install a new app (or "Configure" if AWS Connector for GitHub already exists for your account).
  • Choose your GitHub user as the install target.
  • Repository access: Only select repositories → pick archadv-<you>-hello. Do not grant "All repositories" access.
  • Click Install. The popup returns to the AWS console.
  • Back on the AWS tab, click Connect.

Success looks like: the connection row shows Status: Available (green). Copy the Connection ARN — you will need it in step 5. It looks like arn:aws:codeconnections:us-east-1:123456789012:connection/abcd1234-....

Failure modes:

  • Status stuck on Pending: the GitHub install never completed. Click the connection name → Update pending connection → walk through GitHub install again.

2. Create the CodeBuild project (5 min)

  • Navigate: CodeBuild → Build projects → Create project.
  • Project configuration section:
    • Project name: archadv-<you>-build.
  • Source section:
    • Source provider: GitHub.
    • Credential: Default source credential → CodeConnections → select the connection archadv-<you>-github.
    • Repository: Repository in my GitHub account.
    • GitHub repository: paste the HTTPS URL from step 1a (e.g. https://github.com/<your-gh-user>/archadv-<you>-hello).
    • Source version: main.
  • Primary source webhook events section: leave the webhook box unchecked. CodePipeline (step 5) will trigger builds; we do not want CodeBuild to react to pushes independently.
  • Environment section — use these exact values:
    FieldValue
    Provisioning modelOn-demand
    Environment imageManaged image
    ComputeEC2
    Operating systemAmazon Linux
    Runtime(s)Standard
    Imageaws/codebuild/amazonlinux2-x86_64-standard:5.0
    Image versionAlways use the latest image for this runtime version
    Service roleNew service role
    Role namecodebuild-archadv-<you>-build-service-role (auto-filled — accept it)
    PrivilegedCHECKED — required to run docker build
  • Expand Additional configuration → Environment variables. Add exactly these 3 Plaintext variables (do NOT use Parameter Store / Secrets Manager):
    #NameValueType
    1AWS_ACCOUNT_IDyour 12-digit account IDPlaintext
    2AWS_REGIONus-east-1Plaintext
    3IMAGE_REPOarchadv-<you>-helloPlaintext
  • Buildspec section: Use a buildspec file. Buildspec name: leave blank (defaults to buildspec.yml at repo root).
  • Logs section: CloudWatch Logs checked. Group name: leave blank. Stream name: leave blank.
  • Leave every other field at its default. Click Create build project.

Required: attach ECR permissions to the new service role. The wizard creates a role with CloudWatch Logs + S3 access, but it does NOT include ECR permissions, which the buildspec needs to docker push. Do this immediately after creating the project:

  1. Open a new tab: IAM → Roles.
  2. Search for codebuild-archadv-<you>-build-service-role and open it.
  3. Permissions tab → Add permissions → Attach policies.
  4. Search AmazonEC2ContainerRegistryPowerUser, check it, click Add permissions.

Without this, the first build fails with: User ... is not authorized to perform: ecr:GetAuthorizationToken.

Attach ECR push permission to the CodeBuild service role. The default role can only write CloudWatch Logs — it cannot push to ECR.

  • Navigate: IAM → Roles → search codebuild-archadv-<you>-build-service-role → click into the role.
  • Permissions tab → Add permissions → Attach policies.
  • Search: AmazonEC2ContainerRegistryPowerUser.
  • Tick the box on that AWS managed policy. Click Add permissions.

Success looks like: the role's Permissions tab now lists 2 policies: the auto-created inline CodeBuildBasePolicy-... and the AWS-managed AmazonEC2ContainerRegistryPowerUser.

3. Smoke-test the build (3 min)

  • Navigate: CodeBuild → Build projects → archadv-<you>-build.
  • Click Start build (the orange button, top right). Do NOT click "Start build with overrides".
  • You are redirected to the Build run page. Click the Phase details tab.
  • Watch each phase tick green: SUBMITTED → QUEUED → PROVISIONING → DOWNLOAD_SOURCE → INSTALL → PRE_BUILD → BUILD → POST_BUILD → UPLOAD_ARTIFACTS → FINALIZING → COMPLETED.

Success looks like: top of page shows Status: Succeeded (green) within 3–5 min, and at Amazon ECR → archadv-<you>-hello → Images a new image with tag latest appears with a recent push time.

Failure modes:

  • PRE_BUILD fails with no basic auth credentials: the ECR PowerUser policy was not attached. Re-check step 2's IAM attachment.
  • BUILD fails with Cannot connect to the Docker daemon: Privileged checkbox was not enabled. Edit the project → Environment → tick Privileged → retry.
  • DOWNLOAD_SOURCE fails with Unable to access the GitHub repository: the CodeConnections connection is not Available. Re-check step 1d.

4. Create the artifact bucket (2 min)

CodePipeline needs an S3 bucket to pass artifacts between stages.

  • Navigate: Amazon S3 → Buckets → Create bucket.
  • AWS Region: US East (N. Virginia) us-east-1 (must match the pipeline region).
  • Bucket name: archadv-<you>-pipeline-artifacts-<account-id> (the account-ID suffix avoids the global-uniqueness collision). Example: archadv-jdoe-pipeline-artifacts-123456789012.
  • Object Ownership: ACLs disabled (recommended).
  • Block Public Access settings: Block all public access — checked (the default).
  • Bucket Versioning: Disable (we will not need rollback).
  • Default encryption: SSE-S3 (the default).
  • Tags (optional but advisory by tag policy): Course=archadv, Owner=<you>.
  • Click Create bucket.

5. Create the CodePipeline (7 min)

  • Navigate: CodePipeline → Pipelines → Create pipeline.
  • Creation option (V2 wizard): Build custom pipeline. Click Next.

Step 5a — Choose pipeline settings.

  • Pipeline name: archadv-<you>-pipeline.
  • Execution mode: Queued.
  • Service role: New service role. Role name: auto-fill (accept).
  • Allow AWS CodePipeline to create a service role: checked.
  • Expand Advanced settings:
    • Artifact store: Custom location.
    • Bucket: archadv-<you>-pipeline-artifacts-<account-id> (the bucket from step 4).
    • Encryption key: Default AWS Managed Key.
  • Click Next.

Step 5b — Add source stage.

  • Source provider: GitHub (via GitHub App). (NOT "GitHub (Version 1)" — that is the deprecated OAuth path.)
  • Connection: archadv-<you>-github (from step 1d). Status badge next to it must read Ready to connect or Connected.
  • Repository name: <your-gh-user>/archadv-<you>-hello.
  • Default branch: main.
  • Output artifact format: CodePipeline default.
  • Trigger: No filter (the wizard creates a push trigger on the default branch automatically — you do not need to add one).
  • Click Next.

Step 5c — Add build stage.

  • Other build providers: AWS CodeBuild.
  • Region: US East (N. Virginia).
  • Project name: archadv-<you>-build.
  • Build type: Single build.
  • Click Next.

Step 5d — Add test stage.

  • Click Skip test stage → confirm in the dialog.

Step 5e — Add deploy stage.

  • Deploy provider: Amazon ECS. (NOT "Amazon ECS (Blue/Green)" — that is step 8.)
  • Region: US East (N. Virginia).
  • Cluster name: archadv-<you>-cluster.
  • Service name: archadv-<you>-hello-svc.
  • Image definitions file: imagedefinitions.json (exactly this filename — case-sensitive — matches the artifact written by the buildspec).
  • Click Next.

Step 5f — Review and create. Scroll the summary, confirm 3 stages (Source / Build / Deploy), click Create pipeline.

The pipeline kicks off the first run automatically. Expected total time: 4–6 min.

Success looks like: all 3 stage tiles green, Succeeded badge on each. Deploy stage details link shows "Deployment 1" on the ECS service with Rollout state: COMPLETED.

Failure modes:

  • Source stage red with The provided role does not have permissions to perform this action: the auto-created pipeline service role is missing CodeConnections use. Go to IAM → Roles → AWSCodePipelineServiceRole-... → attach inline policy with codeconnections:UseConnection on your connection ARN.
  • Deploy stage red with imagedefinitions.json: not found: the buildspec didn't produce it. Open the CodeBuild build log, search for UPLOAD_ARTIFACTS — fix the buildspec and re-push.

6. Validate (2 min)

In CloudShell — replace <you>:

ALB=$(aws elbv2 describe-load-balancers --names archadv-<you>-alb --query 'LoadBalancers[0].DNSName' --output text)
curl -s http://$ALB

Success looks like: body is exactly <h1>archadv hello pipeline v3</h1> — Lab 6 served v1/v2, this pipeline pushed pipeline v3 from the GitHub source.

Failure mode: still returns v2 — the deploy stage finished but ECS is still draining old tasks. Wait 60 sec and re-curl, or watch ECS → Services → Deployments tab until Rollout state: COMPLETED.

7. Trigger a re-deploy from a commit (5 min)

In CloudShell, inside the repo directory ~/archadv-<you>-hello:

cd ~/archadv-<you>-hello
sed -i 's/pipeline v3/pipeline v4/' Dockerfile
git add Dockerfile
git commit -m "bump v3 -> v4"
git push origin main

Within 30 sec the CodePipeline page should auto-refresh and show the Source stage In progress (blue). Total run: 3–5 min.

Validate:

curl -s http://$ALB
# Success: <h1>archadv hello pipeline v4</h1>

Failure mode: pipeline does not trigger after the push. Check CodePipeline → archadv-<you>-pipeline → Triggers tab — the GitHub push trigger should be listed. If absent, edit the Source action and set up the trigger manually for branch main on push.

8. Switch to blue/green canary deploy (15 min, optional but high-value)

This step swaps the Deploy provider from "Amazon ECS" (rolling) to "Amazon ECS (Blue/Green)" so CodeDeploy can shift traffic in stages. The ECS service must be re-created because the deployment controller (ECS vs CODE_DEPLOY) is immutable on an existing service.

Step 8a — create a second target group (TG2).

  • Navigate: EC2 → Target groups → Create target group.
  • Target type: IP addresses.
  • Target group name: archadv-<you>-tg2.
  • Protocol: HTTP, Port: 80.
  • VPC: the same Lab 1 VPC used in Lab 6.
  • Health check path: /.
  • Next → register targets page: leave the IP list EMPTY. CodeDeploy registers task IPs automatically.
  • Create target group.

Step 8b — add a test listener on the ALB. Blue/green uses 2 listeners: production (80) + test (8080).

  • Navigate: EC2 → Load balancers → archadv-<you>-alb → Listeners and rules tab → Add listener.
  • Protocol: HTTP. Port: 8080.
  • Default action: Forward to target groups → archadv-<you>-tg2 (weight 1).
  • Add.
  • ALB security group: open inbound to TCP 8080 from 0.0.0.0/0 (so the test listener is reachable for validation). Add a 2nd inbound rule alongside the existing 80 rule:
    #TypePortSource
    1 (existing)HTTP800.0.0.0/0
    2 (add)Custom TCP80800.0.0.0/0

Step 8c — create the CodeDeploy application + deployment group.

  • Navigate: CodeDeploy → Applications → Create application.
  • Application name: archadv-<you>-cd-app.
  • Compute platform: Amazon ECS.
  • Create application.
  • On the application page: Deployment groups → Create deployment group.
  • Deployment group name: archadv-<you>-cd-dg.
  • Service role: choose an existing role with the AWS managed policy AWSCodeDeployRoleForECS. If none exists, create one now: IAM → Roles → Create role → trusted entity AWS service → CodeDeploy → use case CodeDeploy - ECS → name archadv-<you>-codedeploy-role → create. Return to this page and select it.
  • Environment configuration: ECS cluster archadv-<you>-cluster, ECS service (leave blank for now — step 8d creates it).
  • Load balancer: production listener HTTP:80 on archadv-<you>-alb; test listener HTTP:8080 on the same ALB; target group 1 archadv-<you>-tg; target group 2 archadv-<you>-tg2.
  • Deployment configuration: CodeDeployDefault.ECSCanary10Percent5Minutes.
  • Original revision termination: 5 minutes after successful deployment.
  • Create deployment group. (The "ECS service blank" warning is OK — we will edit it after re-creating the service.)

Step 8d — re-create the ECS service with deployment controller CODE_DEPLOY.

  • Navigate: ECS → Clusters → archadv-<you>-cluster → Services.
  • Select archadv-<you>-hello-svc → Update service → desired count 0 → Update → wait until 0 running tasks (~1 min) → back → Delete service → force delete checkbox → confirm.
  • Click Create and repeat Lab 6 step 6 with these changes:
    FieldValue (changed)
    Service namearchadv-<you>-hello-svc (same)
    Deployment options → Deployment typeBlue/green deployment (powered by AWS CodeDeploy)
    Deployment configurationCodeDeployDefault.ECSCanary10Percent5Minutes
    CodeDeploy service rolearchadv-<you>-codedeploy-role
    Load balancing → ListenerProduction: 80:HTTP; Test: 8080:HTTP
    Target groupsTG1: archadv-<you>-tg; TG2: archadv-<you>-tg2
    All other fields (subnets, task SG, public IP off) stay identical to Lab 6 step 6.
  • Create. Wait until 2 tasks RUNNING + target group archadv-<you>-tg shows 2 healthy.

Step 8e — edit the pipeline's deploy stage to use Blue/Green.

  • Navigate: CodePipeline → archadv-<you>-pipeline → Edit → Deploy stage Edit stage → click the Deploy action's pencil icon.
  • Action provider: change to Amazon ECS (Blue/Green).
  • AWS CodeDeploy application name: archadv-<you>-cd-app.
  • AWS CodeDeploy deployment group: archadv-<you>-cd-dg.
  • Amazon ECS task definition: SourceArtifact → taskdef.json.
  • AWS CodeDeploy AppSpec file: SourceArtifact → appspec.yaml.
  • Done → Save.

The pipeline now needs taskdef.json and appspec.yaml in the repo. Add them in CloudShell:

cd ~/archadv-<you>-hello

# Export the current task def revision as JSON
aws ecs describe-task-definition --task-definition archadv-<you>-hello \
  --query 'taskDefinition.{family:family,networkMode:networkMode,containerDefinitions:containerDefinitions,requiresCompatibilities:requiresCompatibilities,cpu:cpu,memory:memory,executionRoleArn:executionRoleArn}' > taskdef.json

# CodeDeploy will substitute <IMAGE1_NAME> with the new image from the build stage
# Replace the image field in container[0] with the placeholder
python3 -c "
import json
with open('taskdef.json') as f: td = json.load(f)
td['containerDefinitions'][0]['image'] = '<IMAGE1_NAME>'
with open('taskdef.json','w') as f: json.dump(td, f, indent=2)
"

cat > appspec.yaml <<'EOF'
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: <TASK_DEFINITION>
        LoadBalancerInfo:
          ContainerName: "web"
          ContainerPort: 80
EOF

# Update the buildspec to write imageDetail.json (CodeDeploy convention for B/G)
cat > buildspec.yml <<'EOF'
version: 0.2
phases:
  pre_build:
    commands:
      - REPO=$AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/$IMAGE_REPO
      - aws ecr get-login-password --region $AWS_REGION | docker login --username AWS --password-stdin $AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com
  build:
    commands:
      - docker build -t $IMAGE_REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION .
      - docker tag $IMAGE_REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION $REPO:latest
      - docker push $REPO:latest
  post_build:
    commands:
      - printf '{"ImageURI":"%s"}' $REPO:latest > imageDetail.json
artifacts:
  files:
    - imageDetail.json
    - taskdef.json
    - appspec.yaml
EOF

sed -i 's/pipeline v4/pipeline v5/' Dockerfile
git add Dockerfile taskdef.json appspec.yaml buildspec.yml
git commit -m "canary: taskdef + appspec + v5"
git push origin main

Step 8f — watch the canary deploy. While the pipeline runs, start a 1-per-second loop in a separate CloudShell tab:

ALB=$(aws elbv2 describe-load-balancers --names archadv-<you>-alb --query 'LoadBalancers[0].DNSName' --output text)
while true; do curl -s http://$ALB | head -c 80; echo; sleep 1; done

Expected timeline (~12–15 min):

  1. Build stage ~3 min.
  2. Deploy stage opens CodeDeploy deployment. Replacement task set provisions on TG2 (~2 min).
  3. CodeDeploy shifts 10% of production listener traffic to TG2. You will see roughly 1 in 10 responses flip to pipeline v5 while the other 9 remain pipeline v4.
  4. After 5 min wait, CodeDeploy shifts 100% — all curl output is pipeline v5.
  5. 5 min later, the original task set terminates.

Failure mode: deployment hangs at BeforeAllowTraffic hook for 10+ min — CodeDeploy role is missing permission to register targets. Re-attach AWSCodeDeployRoleForECS to the role.

Validation checklist

Cleanup

  1. CodePipeline → archadv-<you>-pipeline → Delete pipeline.
  2. CodeBuild → archadv-<you>-build → Delete.
  3. If you did step 8: CodeDeploy → archadv-<you>-cd-app → delete (deletes the deployment group too). Then delete archadv-<you>-tg2 and the ALB's 8080 listener.
  4. S3 → archadv-<you>-pipeline-artifacts-<account-id> → Empty, then Delete.
  5. Developer Tools → Settings → Connections → archadv-<you>-github → Delete.
  6. Revoke the GitHub PAT: github.com → Settings → Developer settings → Fine-grained tokens → archadv-cloudshell → Delete.
  7. Leave ECS service / cluster / ECR repo running — Lab 8 does not use them, but Lab 6's cleanup section handles them at end of day.

Stretch goals

  • Add a Manual approval action between Build and Deploy. Pipeline pauses; you click Review → Approve to continue. Useful for production gates.
  • Add a CloudWatch alarm on ECS task UnhealthyHostCount > 0 and add it as a CodeDeploy auto-rollback alarm in the deployment group. Push a broken Dockerfile (e.g., bad CMD) and watch CodeDeploy roll back automatically during canary.
  • Add a CodeBuild stage that runs trivy image against the just-pushed tag and fails the pipeline on HIGH/CRITICAL CVEs.
