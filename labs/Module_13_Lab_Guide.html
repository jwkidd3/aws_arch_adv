Advanced Architecting on AWS

Lab 13 — DMS console build (replication instance + endpoints + task)

Cost warning — read first. The replication instance (dms.t3.small) costs ~$0.07/hr while it exists, even before any task runs. You must delete the replication instance at the end of class — see Cleanup. Forgotten DMS instances are the #1 lab cost overrun.

Objective

Build the AWS Database Migration Service (DMS) infrastructure for a homogeneous MySQL → S3 migration: replication instance, source + target endpoints, migration task. You will not start the task — there's no real source database. The point is to experience the DMS wizards and understand what each piece is for.

Time budget: 30 minutes

Throughout, replace <you> with your slug. Region: us-east-1. We'll use the Lab 1 VPC (still up from Day 1).

Pre-flight

  1. Sign in to Sandbox<N>. Confirm role badge top-right reads AWSAdministratorAccess @ Sandbox<N>.
  2. Region: US East (N. Virginia) us-east-1.
  3. Open CloudShell.
  4. Identify the Lab 1 VPC. Navigate VPC → Your VPCs; note the VPC ID with Name tag archadv-<you>-vpc. Note both public subnet IDs (archadv-<you>-public-a and archadv-<you>-public-c) — DMS needs ≥2 subnets in ≥2 AZs.

Steps

1. Replication subnet group (3 min)

DMS requires a subnet group before the replication instance. The Create-replication-instance wizard offers an inline create, but it silently fails when the wizard form is incomplete — pre-create it.

  • Navigate: AWS DMS → Subnet groups → Create subnet group.
  • Name: archadv-<you>-lab13-sng
  • Description: archadv lab 13 DMS subnet group
  • VPC: Lab 1 VPC
  • Add subnets: tick both archadv-<you>-public-a and archadv-<you>-public-c.
  • Create subnet group.

2. Replication instance (3 min to start; ~10 min to provision)

Start this first — it provisions in the background while you build the endpoints and task.

  • Navigate: AWS DMS → Replication instances → Create replication instance.
  • Name: archadv-<you>-lab13-ri
  • Description: archadv lab 13 RI
  • Instance configuration:
    • Instance class: dms.t3.small (cheapest available; ~$0.07/hr).
    • Engine version: leave the default pre-selected value (it'll be a specific version number like 3.5.x — that IS the newest stable; do not change it).
    • High Availability: Dev or test workload (Single-AZ)
  • Storage: 50 GB (default; do not change).
  • Connectivity and security:
    • VPC for IPv4 endpoints: Lab 1 VPC
    • Replication subnet group: archadv-<you>-lab13-sng (the one you just made).
    • Availability zone: No preference.
    • VPC security group(s): leave the default SG of the Lab 1 VPC.
    • Public accessibility: Yes. (For the lab — production should be No with private connectivity to the source DB.)
  • Advanced settings: KMS key (default) aws/dms.
  • Maintenance: Auto minor version upgrade: Off.
  • Tags: Course = archadv, Owner = <you>.
  • Create.

The instance shows status creating and takes ~10 min to reach available. Move on to Step 3 immediately — don't watch it.

Failure mode: if you see "DMS replication instance creation is not supported in the requested availability zone", this means dms.t3.small is unavailable in one of the AZs. Delete the RI, return to Step 1, change the subnet group to use different public subnets (the Lab 1 VPC has subnets across a + c — if c is the issue, try a + b). Flag the instructor.

3. Source endpoint — MySQL placeholder (4 min)

  • Navigate: AWS DMS → Endpoints → Create endpoint.
  • Endpoint type: Source endpoint.
  • Do not tick "Select RDS DB instance" — we're faking a non-existent on-prem source.
  • Endpoint identifier: archadv-<you>-lab13-source
  • Source engine: MySQL
  • Access to endpoint database: Provide access information manually
  • Server name: placeholder.example.com
  • Port: 3306
  • User name: dmsuser
  • Password: placeholder
  • Secure Socket Layer (SSL) mode: none
  • Test endpoint connection (optional): skip. (Would fail — there's no real MySQL.)
  • Create endpoint.

After creation the endpoint shows Status Active with connection status Untested. That's the goal state.

4. S3 target bucket and target endpoint (7 min)

S3 is the realistic target for a "lift to data lake" migration.

4a — bucket:

  • Navigate: S3 → Create bucket.
  • Bucket name: archadv-<you>-lab13-target
  • Region: us-east-1
  • Block Public Access: leave default (all four blocked).
  • Create bucket.

4b — IAM role for DMS → S3:

  • Navigate: IAM → Roles → Create role.
  • Trusted entity: Custom trust policy. Paste:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "dms.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
  • Next. Permissions: tick AmazonS3FullAccess (lab scope; production should be a scoped inline policy on this one bucket). Next.
  • Role name: archadv-<you>-lab13-dms-s3-role. Create role.
  • Open the role and copy the Role ARN from the top of the role detail page — you'll paste it in 4c.

4c — target endpoint:

  • Navigate: AWS DMS → Endpoints → Create endpoint.
  • Endpoint type: Target endpoint.
  • Endpoint identifier: archadv-<you>-lab13-target
  • Target engine: Amazon S3
  • Service access role ARN: paste the ARN from 4b.
  • Bucket name: archadv-<you>-lab13-target
  • Bucket folder: dms-migration/
  • Endpoint settings: leave defaults (CSV, no compression).
  • Create endpoint.

5. Database migration task (5 min)

By now the replication instance should be available (or close). If still creating, proceed — you can save the task either way.

  • Navigate: AWS DMS → Database migration tasks → Create task.
  • Task identifier: archadv-<you>-lab13-task
  • Replication instance: archadv-<you>-lab13-ri
  • Source database endpoint: archadv-<you>-lab13-source
  • Target database endpoint: archadv-<you>-lab13-target
  • Migration type: Migrate existing data (full load).
  • Task settings:
    • Editing mode: Wizard (defaults are fine for the lab).
    • Target table preparation mode: Do nothing
    • LOB column settings: Limited LOB mode, 32 KB.
  • Table mappings:
    • Editing mode: Wizard.
    • Click Add new selection rule.
    • Schema: Enter a schema → mydb.
    • Source name: % (wildcard — all tables).
    • Action: Include.
  • Migration task startup configuration: Manually later. (Do not auto-start — there's no source.)
  • Create task.

The task transitions to Ready. That's the lab outcome.

6. Inspect the task (3 min)

  • Click into the task name from the migration-tasks list.
  • Table mappings tab — review the JSON; note the rule-type: "selection" block for schema/table inclusion.
  • Migration task assessment tab — click Run new assessment if the RI is available. With our placeholder source, the assessment will fail with a connection error. That's the expected outcome — you've seen the screen students should recognise in production.
  • Logs and Statistics tabs are empty (task hasn't run).

Validation checklist

Cleanup — DO THIS BEFORE THE NEXT BREAK

The replication instance bills ~$0.07/hr until deleted. Leaving it overnight is ~$1.70/student. Delete it.

In this exact order (each step blocks on the prior):

  1. AWS DMS → Database migration tasks → tick the task → Actions → Delete (task must be Ready or Stopped, not Running; ours never ran so it's Ready). Confirm.
  2. AWS DMS → Endpoints → tick archadv-<you>-lab13-source → Actions → Delete. Repeat for archadv-<you>-lab13-target.
  3. AWS DMS → Replication instances → tick archadv-<you>-lab13-ri → Actions → Delete. Type delete me to confirm. Watch the row disappear. If it's stuck in deleting for > 5 min, post in chat.
  4. AWS DMS → Subnet groups → tick archadv-<you>-lab13-sng → Delete.
  5. S3 → archadv-<you>-lab13-target → Empty, then Delete.
  6. IAM → Roles → archadv-<you>-lab13-dms-s3-role → Delete.

Do NOT delete the Lab 1 VPC. The capstone lab reuses it.

Stretch goals (only if you finish early)
